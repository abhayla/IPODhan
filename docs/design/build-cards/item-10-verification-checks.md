# Item 10 — The verification checks of §4

## Purpose

After this ships, every one of the fourteen checks §4 names is a script with an exit code, a healthy
value, a place it runs, and an alarm route through the shared Notifier gateway — closing **F-30**, which
is open today because four of the six existing gates in this design are prose, not code that can fail a
build or page anyone.

## Serves

§4 ("How we would know it worked") in full — all fourteen check ids in its table
(`PULL-PLAN`, `PULL-WALK`, `PULL-YIELD`, `PULL-EXCUSED`, `PULL-EXHAUST`, `PULL-NOOP`, `PULL-NOBLANK`,
`PULL-WRITE`, `PULL-FROZEN`, `PULL-ADMIN`, `PULL-TYPE`, `E1-SOURCE`, `REREAD-RECEIPT`,
`REREAD-VERDICT`, `REREAD-LATENCY`) plus the roster meta-check `CHECK-ROSTER`, and finding **F-30**
named directly in §7.1 row 10. Also serves `signal-ownership.md` R3 (every nightly signal needs a
same-day diffing consumer) and R6 (failures carry their cause) — this item is that consumer for the pull
model's own signals. Depends on item 6 (the pull walk — most checks read its output) and item 9 (the
re-read loop — the three `REREAD-*` checks read its output); §7.1 row 10 lists both.

## Schema

No schema change. Every check reads `ipo_field_plan` (item 5/6), `field_sources`, `data_conflicts`
(existing tables), and the re-read receipt columns item 9 adds — nothing here defines a new column.
State needed to compute NEW/GONE/SAME per check-run (the `signal-ownership.md` R3 requirement, and the
same pattern `audit-detection-floor.mjs` already uses per its `"audit's own state dir on the box"`
comment at line 158 of that script) is a JSON state file per script under the audit's existing state
directory (`scripts/state/` (LOCAL), already present in this worktree per `git status` — not a DB table). (NEW)

## Interfaces

Every script follows the exit-code convention `docs/reviews/detection-checks/_meta.json` already
establishes for the existing detection-floor audit, reused verbatim rather than invented fresh:

```
exit 0  — every check in this script PASSed
exit 1  — at least one check FAILed (a defect is live)
exit 2  — the script itself crashed or could not start (signal-ownership.md R6: never silent)
exit 3  — no FAIL, but at least one check is UNVERIFIABLE (blind, not green — dominated by exit 1 if both occur)
```

```ts
// shared shape every new script emits per check, before the human-readable digest —
// this is what CHECK-ROSTER (§4) verifies is present for every id every night.
interface CheckResult {
  id: string;              // e.g. 'PULL-YIELD'
  status: 'PASS' | 'FAIL' | 'UNVERIFIABLE';
  healthy: string;         // the healthy-value description from §4's table, verbatim
  value: unknown;          // what was actually measured tonight
  failingIdentities?: Array<{ ipoId: string; field?: string; reason: string }>; // signal-ownership.md R1 — never a bare count
  cause?: string;          // signal-ownership.md R6 — every failure carries its cause
}
```

## Feature flag

No flag — these are read-only audit scripts, not a code path users hit. They are wired into the nightly
cron and CI, both of which are themselves gated on nothing beyond the scripts existing and being
executable (per the existing `j_cron_executable` detection check, which already guards this exact class
of defect — a cron script committed without the execute bit).

### The fourteen checks, concretely — part of Interfaces

| Check id | Asserts | Healthy | Runs | Alarm route |
|---|---|---|---|---|
| `PULL-PLAN` | plan rows per IPO = the committed manifest; manifest hash unchanged | equal | nightly audit (`audit-pull-plan.mjs`) | `notifyOwner('P1', 'PULL-PLAN mismatch', {...})` — `dedupeKey: 'pull-plan-<date>'` |
| `PULL-WALK` | every phase-1 IPO walked this slot | 19 of 19 (phase-1 count ≥ 1 asserted separately) | per data-job cycle AND nightly rollup | P1 if fewer than all, twice running; the phase-1-count≥1 sub-check pages P0 if it ever hits 0 (that would mean the whole walk stopped) |
| `PULL-YIELD` | share of document-printable fields supplied round 1 | rising toward 100%; UNVERIFIABLE if denominator moved >5% overnight | nightly (`audit-pull-yield.mjs`) | P2 digest on a fall; P1 if UNVERIFIABLE two nights running (a denominator that keeps moving is itself a defect) |
| `PULL-EXCUSED` | `NOT_PRINTED` count per (IPO, document type), NEW vs yesterday by name | stable | nightly, same script | P1 — "any growth" per §4, never batched into the daily digest |
| `PULL-EXHAUST` | `EXHAUSTED` rows by (IPO, field, reason), NEW vs GONE vs SAME | shrinking | nightly, same script | P1 on any NEW row on a phase-1 IPO (signal-ownership.md R4: NEW beats standing) |
| `PULL-NOOP` | writes per cycle ÷ fields re-asked per cycle | near zero, no filing that day | per cycle (`audit-pull-writes.mjs` run in cycle-summary mode) | P2 digest; P1 if it rises with no matching document arrival |
| `PULL-NOBLANK` | fields that went from a value to absent this slot | 0 | per cycle, same script | P0 — this is the direct guard on OD-7 (a value is kept and marked stale, never blanked); any non-zero pages immediately, not digested |
| `PULL-WRITE` | plan rows marked `SUPPLIED` whose write returned `skipped` | 0 | per cycle, same script | P1 — the exact false-clean state §2.3 warns about (`skipped: true` from a lock miss recorded as success) |
| `PULL-FROZEN` | `SUPPLIED` rows whose `chosen_document_id` has been superseded | 0 | nightly, same script | P1 — guard on §2.5 |
| `PULL-ADMIN` | fields skipped for admin reasons with no live protection row | 0 | nightly, same script | P1 — guard on §2.7 |
| `PULL-TYPE` | resolved ranks match the IPO's current offering type; IPOs with a null segment | 0 / 0 | nightly, same script | P1 |
| `E1-SOURCE` | for the ten E-1 timetable fields, `field_sources.source` is never `DRHP` | true | nightly (`audit-pull-writes.mjs`) | P0 — a document overwriting a timetable field is a direct violation of an owner decision (OD-2/E-1), not a data-quality nit |
| `REREAD-RECEIPT` | re-reads with a receipt hashed this cycle ÷ re-reads recorded | 1.0 | nightly (`audit-reread-loop.mjs`), depends on item 9 | P0 below 1.0 — this is the exact "confirming a wrong value forever" failure mode §3.2 names |
| `REREAD-VERDICT` | share of re-reads ending `verified_against_document` over 7 days | below 0.95 | nightly, same script | P2 digest at/above 0.95 (a source "never wrong" is a source never actually consulted — worth watching, not paging) |
| `REREAD-LATENCY` | oldest actionable disagreement with no re-read attempt | under 48h | nightly, same script | P1 over 48h, listed by IPO and field (never a bare count, per signal-ownership.md R1) |
| `CHECK-ROSTER` | every id above appears in tonight's report | all present | nightly, wraps all four new scripts' output | P0 — "a check that crashed must not read as no findings"; this is the one check that reads the OTHER four scripts' exit codes, not the database |

Every `P1`/`P0` row above additionally files or comments on a GitHub issue when it is a phase-1 IPO,
per `signal-ownership.md` R2 (a failure needs an issue number before it can be called "known") — reusing
`scripts/audit-findings-to-issues.mjs`'s existing sync pattern (already step 4 of
`vps-data-audit-cron.sh`) rather than building a second issue-filer.

**`dedupeKey` convention**, following the existing `detection-checks/_meta.json` paging model verbatim:
`pull-<checkId>-<YYYY-MM-DD>` for a FAIL digest, `pull-<checkId>-unverifiable-<YYYY-MM-DD>` for
UNVERIFIABLE — date-scoped so the Notifier gateway's 30-minute cooldown (`GLOBAL.md` §2) cannot swallow
a nightly digest the way a bare `dedupeKey` would.

## Detection

This item **is** the detection change for items 6, 7 and 9 combined — it is not itself subject to
`.claude/rules/recurrence-detection-gate.md` in the sense of needing a *further* detection check (it does
not touch `scraper/src/services/**` or `scraper/src/scrapers/**` write paths directly), but every one of
its fourteen checks is registered under `docs/reviews/detection-checks/` specifically so a future PR
touching those write paths is checked against this registry by the existing `detection-change-gate` CI
job, closing F-30.

## Staging proof

The exact log line: a staging run of `vps-data-audit-cron.sh` (or each new script standalone against the
staging DB via the tunnel, per `docs/ops/prod-ops-recipes.md` §1) producing all fourteen `CheckResult`
rows plus `CHECK-ROSTER: all present`, with at least one real PASS/FAIL/UNVERIFIABLE value that is not a
placeholder — per §4's own words, "None of this is evidence until it has run against real data... a
passing unit test is not proof, and neither is a clean read taken immediately after a repair." Healthy
value: exit 0 (or exit 3 with a named, expected UNVERIFIABLE reason — e.g. `PULL-YIELD` UNVERIFIABLE on
the very first run because there is no "yesterday" denominator yet). Which cycle carries it: the first
nightly cron run on staging after items 6, 7, 9 and this item are all live there — this item cannot be
proven standalone before its dependencies exist.

## Rollback

Revert the commit; remove the four steps from `vps-data-audit-cron.sh`; remove the four new registry
entries and regenerate `detection-checks.json`. Fully reversible — these are read-only scripts with no
write path of their own; nothing they touch is data that needs repairing on rollback. Nothing here
disables `owner-notify.ts` itself, so removing this item does not affect any other alert already routed
through it.
