# Item 20 — the design-traceability CI check

Module: `verification`. Serves OD-52 and §8.5.

## Purpose

After this ships, "the code implements this design" stops being a claim anybody has to take on trust:
a pull request fails when a design rule has no build item, a build item's rule has no test, a test
names a rule that does not exist, or a rule's wording changes without its card and test being touched
in the same change.

## Serves

- **OD-52** (owner, 2026-09-09): *"How will the implementation prove it has followed this design, rule
  by rule?"*
- **§8.5** — the mechanism in full, and the honest limit of it.
- **§7.6** — the module-boundary import rule ships in the same item, because it answers the same
  question in the other direction: does the code still have the SHAPE the design says it has.
- It closes nothing in `findings.json`; it is the machinery that stops the next class of finding
  being discovered by a person reading 3,000 lines.

## Interfaces

`node scripts/ci/check-design-traceability.mjs` — exit 0 clean, 1 a broken link in the chain, 2 the
check itself failed. It reads, and never writes:

- `docs/design/rules.json` — the live rule ids;
- `docs/design/build-cards/item-*.md` — each card's rules-implemented block;
- `docs/design/rules-unclaimed.json` (NEW, written by `apply-rule-ownership.mjs`) — ids declared as policy;
- every test file under `scraper/tests/**`, `web/tests/**`, `packages/*/tests/**` and
  `scripts/tests/**` — for `// implements: R-nnn` headers;
- `git diff --name-only <base>...HEAD` — for failure mode 4 only.

The four failure modes, which are the whole contract:

1. **A live rule id is claimed by no build card and not declared unclaimed.** (Design gate D19 already
   asserts this; CI asserts it again because a card can change in a pull request that never runs the
   design gate.)
2. **A card claims a rule id that no test declares.** The card promised an implementation; nothing
   tests it.
3. **A test declares an id that is not live** — a typo, or an id retired when its rule was reworded.
4. **A rule's hash changed and neither its owning card nor a test that names it is in the diff.**
   **Corrected 2026-09-10, proven on real data during build (lane B, slice 2).** Mode 4 is a BACKSTOP
   against `rules.json` being edited by hand, resolved by a merge, or written by a changed generator.
   It is NOT what catches an edited design sentence, and the earlier claim that it was "the mode that
   earns the check" was wrong. `generate-rule-index.mjs:158` matches previous rules **by hash**
   (`new Map(prev.rules.map(r => [r.hash, r]))`), so editing a sentence RETIRES the old id and MINTS a
   new one - it never produces the same-id/different-hash state mode 4 waits for. Measured: editing one
   line of the design and running the generator gave `SAME ID / DIFFERENT HASH: []`, `NEWLY RETIRED:
   ["R-153"]`, `NEW IDS: ["R-181"]`. **The sentence-edit case is caught by mode 1** - the new id is live
   and claimed by no card, so the pull request fails (`MODE 1 - 1 live rule(s) claimed by no build card
   ... R-181`, exit 1). Mode 4 still earns its place: `rules.json` is a committed, hand-editable file and
   mode 4 is the only arm that would see it drift.

   **Known gap, found the same day and not closed by this item.** When a sentence edit retires an id, the
   card that claimed it is left claiming a RETIRED id, and NO arm of this check catches that: mode 1 is
   live-only, mode 2 skips non-live ids, mode 3 is test-side, mode 4 filters retired. It IS caught by
   `docs/design/check-design-consistency.mjs` D19 (`1 card(s) claim a retired or unknown rule id`), but
   only under `--gate`, and neither script is wired into any workflow today - so at the time of writing it
   is caught by nothing that runs. Wiring D19 belongs with slice 4's CI wiring.


`node scripts/ci/check-module-boundaries.mjs` — exit 0 / 1 / 2, same shape. It maps each source file
to one of the ten modules in §7.6 by path, builds the import graph, and fails on an edge that points
up the layer order (`discovery` → `download` → `extraction` → `validation` → `consolidation`, then
`plan`, `walk`, `verification`, `re-read`, and `read-side` above all of them).

## Feature flag

None, and deliberately: a gate behind a flag is a gate somebody turns off on a Friday. It lands
switched on, and its failure-mode-2 arm ships in **reporting** mode (exit 0, printing the count)
until the release that carries item 6, when the first real tests declaring rule ids exist. That flip
is one line, and it is named here so nobody has to guess when it is due.

## Tests

- `scripts/ci/tests/check-design-traceability.test.mjs` (NEW) — one case per failure mode, each RED
  BEFORE GREEN: a fixture rule index with an unclaimed id; a card claiming an id no test declares; a
  test declaring `R-999`; and a hash change with an untouched card. A gate that has never been red is
  not a gate (`docs/design/implementation-ready-report-2026-09-09.md` §9, learning 1).
- `scripts/ci/tests/check-module-boundaries.test.mjs` (NEW) — a fixture tree with one upward import,
  asserting exit 1 and the named edge; and a clean tree asserting exit 0.
- Both self-tests run as their own CI step BEFORE the gate step, exactly as the repair-tool lint does
  (`.github/workflows/pr-gate.yml:108`), so a broken check cannot pass as a clean repository.

## Detection

The check IS the detection for its own class. Registered as `design_traceability` in
`docs/reviews/detection-checks/` with the consumer `per-cycle failure reading (identities)` — a pull
request gate reports by identity (which rule, which card, which test) and never as a count, per
`.claude/rules/signal-ownership.md` R1.

Its own worst failure — passing because it found no rules at all — is guarded the way D18 guards
itself: zero live rules is a FAIL, not a pass.

## Staging proof

There is no staging proof, and that is not an omission: this item ships no runtime behaviour. Its
proof is a CI run. The named line is the pull-request-gate step **`Design traceability (OD-52)`**
printing `155 rules, 155 claimed, 0 orphans` on a clean pull request, and exit 1 naming the offending
id on one that deletes a card's rule line. Both are demonstrated in the item's own pull request.

## Rollback

Revert the commit. No data is written, no schema changes, and the two workflow steps are additive —
removing them returns the gate to exactly what it does today. The only lasting artefact is
`docs/design/rules.json`, which is a documentation file and harmless on its own.

## Tier, budget and cost

**Tier A.** It is a CI gate, and `engineering-roles.md`'s review-tier rubric puts a gate that runs on
every pull request in Tier A regardless of its size — this one can block every merge in the
repository if it is wrong.

`Budget: 90 min wall-clock, 120 tool calls.`

Cost: small in code, high in blast radius. One fresh-Opus adversarial review with mutation tests on
every arm, per Tier A. It sits in release R1 (§7.5) because every later release is proved by it.

## Known gaps

- **It proves conformance to the rules as written, never that the rules are right.** §8.5 says this
  plainly and so does this card: a design can be faithfully implemented and still be wrong about the
  world. The walkthroughs, the probes and the review rounds are what test the rules themselves.
- **The rule extraction is deliberately broad** (any paragraph carrying *must*, *never* or *always*),
  so some ids are not really rules. The cost is a stray line in a card; the alternative — a narrow
  extraction that misses real rules — is the failure this exists to prevent. If the noise becomes
  the complaint, the fix is to tighten the generator and let the retire-and-renumber mechanism carry
  the change through the cards.
- **Failure mode 2 ships in reporting mode** until item 6 lands, as stated under Feature flag. Until
  that flip, a card can claim a rule with no test and CI will only say so.
