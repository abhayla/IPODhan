▶What “customizable” means, and how it is testedSwap Test NOT RUNThe split between capability (decided by reality, not configurable) and priority (the owner’s, pure configuration) — and the Swap Test, the acceptance test for the whole stage.

The owner's words (OD-51): "when I said change the source of the field from currently one to three, you should just make a small customization change, not a code change." The design (§2.3.5) splits the requirement into two things, and only one of them is configurable:

Capability
Can this source serve this field at all?

Decided by reality, proven by fetching. Not configurable. Nobody may rank BSE first for issue size while BSE is measured 41 to 76 percent low.

Priority
Of the sources that can, which do we prefer?

Decided by the owner. Pure configuration. Swapping rank 1 and 2, or adding a third capable source, never needs a code change or a build.

Acceptance test for the whole stage: the Swap Test. On staging, swap rank 1 and rank 2 of ipos.issue_size (DOC and CHITTORGARH) twice, once through each configuration path, and show at the next wake that (a) the plan row's ranks changed, (b) the walk asked the new rank 1 first, (c) the writer accepted the new rank 1 over the stored value, (d) provenance names the configuration version that produced it, then swap back. If this test cannot be run by the supervisor with zero code edits, stage 3 is not done.

▶How a change reaches production without a buildS5 landedThe config-only deploy path: what deploy-config.sh copies, why releases stay immutable, how rollback works.

Today there is no config-only path: every change to scraper/config/ rides a full build on the 2-vCPU box that serves production. The design chose the config-only deploy path over a database-held config (§7.6), because git gives a diff, a reviewer, a date and a revert. Slice S5 builds it:

  1. scripts/ops/deploy-config.sh --slot staging|prod --sha <merged main sha> --reason "..." copies only scraper/config/field-manifest.json from that sha into $ROOT/shared/config/<slot>/ (never into a release: releases stay immutable, review finding 7), verifies the file hash, writes CONFIG_SHA, and appends a log line with who, when, sha and reason. Every release's own scraper/config/field-manifest.json is a symlink to that shared file.
  2. No build, no PM2 restart: the next wake is a fresh process and validates the file at start. The cycle log's manifest-hash line is the proof the new file is live.
  3. Guarded like every deploy: staging any time with the logged reason; prod only on the owner's word. Because it is not a build, the recommendation is to allow a prod config deploy in any evening window, not only the weekly one. This is an owner decision (D-3 below).
  4. Rollback is the same command with the previous sha.

What the first plan got wrong, and how it was caught

The implementation plan failed its independent review with four CRITICAL findings, every one reproduced before acceptance. Recording them because the pattern matters more than the fixes:

  • A headline measurement was a tautology. "All 8,010 field instances have one source, so the cross-check never ran" — but field_sources has a unique constraint making one row per field by construction. It would read 8,010/8,010 even if three witnesses voted. The real finding is stronger: the schema cannot record a second witness at all.
  • The flagship proof named an impossible source. It said NSE and the document both answer issue_size; NSE is marked capable: false for that field because it computes issue size excluding the OFS portion. A worker would have fabricated the proof.
  • OD-56 was implemented by no slice — the owner's first and most load-bearing decision. Now S5.
  • The zero rule was backwards. data-consolidation-service.ts already warns: "the emptiness test is === null || === undefined, never falsiness: 0, false and '' are values a source genuinely supplied." The plan said the opposite and would have reversed a deliberate guard on 33 fields where zero is real.

S0's finding killed the problem instead of solving it. All 1,683 zero-conflicts are one field — issueSize — and 1,659 of them (98.6%) came from Moneycontrol, which OD-3 retired. The last was written on 1 September, 17 days ago. So the comparator carve-out for zero is unnecessary: the problem was a source, and the source is already gone. Chittorgarh (21) and BSE (3) account for the rest, both stopped weeks ago.

What this does not do, stated plainly

  • It does not fix the 14,145 existing conflicts. The model prevents new ones; draining the old pile is the admin queue's job (S9).
  • It does not make the single-witness fields trustworthy. Shape validation catches a malformed value, not a wrong one — and no second witness exists to catch a wrong one.
  • It does not add a new external source yet. The four existing witnesses vote first and the gaps get measured; SEBI's filing portal is the named candidate if one is wanted later.
