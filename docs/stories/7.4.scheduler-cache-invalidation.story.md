# Story 7.4: Scheduler & Cache Invalidation

**Workflow:** automated-story-creation-workflow

## Story
**As a** IPODhan platform administrator,
**I want** an automated job scheduler that runs scrapers at defined intervals (15/30/60 minutes based on market hours) and implements comprehensive cache invalidation strategy,
**so that** the platform displays real-time IPO data without manual intervention, ensuring users always see fresh information updated automatically during market hours and maintaining optimal performance through effective cache management.

## Acceptance Criteria
1. Node-cron installed and configured with all schedule expressions for market hours, after hours, and weekends
2. NSE scraper job runs automatically according to schedule: Every 15 minutes during market hours (9 AM-5 PM weekdays), every 30 minutes after hours (5 PM-9 AM weekdays), every 1 hour on weekends
3. BSE scraper job runs automatically according to schedule: Every 15 minutes during market hours (9 AM-5 PM weekdays), every 30 minutes after hours (5 PM-9 AM weekdays), every 1 hour on weekends
4. Health check job runs every 5 minutes and logs warnings/alerts when scrapers haven't run successfully in over 1 hour
5. Daily summary job runs at 8 AM and generates comprehensive report including total IPOs scraped, success/failure rates, subscription updates, average duration, and errors
6. Cache invalidation service invalidates all relevant cache keys after successful scraper run: `ipos:list:*`, `ipo:{slug}`, `subscription:latest:{slug}`, `dashboard:stats`
7. Cache invalidation sets `last_scraped_at` timestamp in database for each successfully updated IPO
8. Scheduler supports graceful shutdown on process termination (SIGTERM, SIGINT) and stops all jobs cleanly
9. Mutex/lock pattern prevents overlapping scraper runs using Redis-based distributed locks
10. Environment variables control scraper enable/disable (`SCRAPER_ENABLED=true/false`) and interval mode (`SCRAPER_INTERVAL_MODE=dev/prod`)
11. Structured logging implemented for all scheduled jobs: log start, end, duration, status (success/failure), IPO count
12. Manual test: Start scheduler and verify jobs execute at correct times with proper intervals
13. Integration test: Verify cache invalidation works end-to-end after scraper runs

      this.jobs.forEach(job => job.stop());

      // Wait for running jobs to complete (with timeout)
      await this.waitForRunningJobs(30000); // 30 second timeout

      // Release all job locks
      await this.lockManager.releaseAllLocks();

      process.exit(0);

    private async executeJob(jobName: string, handler: JobHandler): Promise<void> {
      const startTime = Date.now();
      logger.info({ job: jobName }, 'Job started');

      try {
        // Acquire lock (skip job if lock already held)
        const lockAcquired = await this.lockManager.acquireLock(jobName, LOCK_TTL);
        if (!lockAcquired) {
          logger.warn({ job: jobName }, 'Job skipped: lock already held');
          return;
        }

        // Execute job handler
        const result = await handler();

        // Release lock
        await this.lockManager.releaseLock(jobName);

        const duration = Date.now() - startTime;
        logger.info({
          job: jobName,
          status: 'success',
          duration,
          result
        }, 'Job completed successfully');

      } catch (error) {
        const duration = Date.now() - startTime;
        logger.error({
          job: jobName,
          status: 'failure',
          duration,
          error: error.message,
          stack: error.stack
        }, 'Job failed');

        // Release lock on error
        await this.lockManager.releaseLock(jobName);
      }
    }

### Cache Invalidation Strategy

**Source:** [docs/architecture/api-specification.md#caching-strategy] and Epic 7

**Cache Keys to Invalidate:**
- `ipo:detail:{slug}` - Specific IPO detail page cache (TTL: 30 minutes)
- `ipos:list:*` - All IPO listing cache variations (TTL: 15 minutes)
  - Example keys: `ipos:list:status=open`, `ipos:list:status=open&category=SME&page=1`
- `ipo:search:*` - All IPO search result caches (TTL: 15 minutes)
- `subscription:latest:{slug}` - Latest subscription cache (TTL: 5 minutes)
- `subscription:history:{slug}:*` - Subscription history cache (TTL: 10 minutes)
- `dashboard:stats` - Dashboard statistics cache (TTL: 10 minutes)

**Invalidation Pattern:**
1. After successful scraper run: invalidate all cache keys for updated IPOs
2. Use Redis SCAN for pattern matching (non-blocking, production-safe)
3. Batch delete keys using Redis pipeline for performance
4. Log invalidation operations (keys deleted, duration)
5. If Redis connection fails: log error, do NOT crash scraper (cache miss is acceptable)

**Cache-Aside Pattern (from Story 2.3):**
- API routes check Redis first
- On cache miss: query DB, populate cache with TTL
- On data update: explicit cache invalidation (no auto-invalidation)

### Error Handling Strategy

**Source:** [docs/architecture/error-handling-strategy.md] and Epic 7

**Scheduler Error Handling:**
1. **Job Execution Failures:**
   - Catch all errors in job execution wrapper
   - Log error with context (job name, duration, error message)
   - Release job lock if held (prevent deadlock)
   - Do NOT crash scheduler (other jobs continue running)
   - Failed jobs retry on next scheduled interval

2. **Job Lock Failures:**
   - If lock acquisition fails: skip job execution, log warning
   - If lock release fails: log error, continue (Redis TTL will expire lock)
   - If Redis connection fails: log error, skip lock (job runs without lock - risky but acceptable)

3. **Cache Invalidation Failures:**
   - If Redis connection fails: log error, do NOT crash scheduler
   - Cache miss is acceptable (data will be re-fetched from DB)
   - Retry failed invalidations (3 attempts with backoff)

4. **Database Query Failures:**
   - Health check: return 'UNKNOWN' status, log error, do not crash
   - Daily summary: log error, skip summary generation, do not crash

5. **Graceful Shutdown:**
   - On SIGTERM/SIGINT: stop accepting new job executions
   - Wait for running jobs to complete (with timeout)
   - Release all job locks
   - Close database and Redis connections
   - Exit with code 0

**Error Logging Format (Pino):**
```typescript
logger.error({
  error: error.message,
  stack: error.stack,
  context: { jobName, duration, attempt },
  timestamp: new Date().toISOString()
}, 'Job execution failed');
```

### Risks and Mitigation

**Source:** Epic 7

**Risk 1: Scheduler Crashes or Stops Unexpectedly**
- **Impact:** Scrapers don't run, data becomes stale
- **Mitigation:**
  - Use PM2 for process management (auto-restart on crash)
  - Implement graceful shutdown (prevent abrupt termination)
  - Health checks provide early warning
- **Contingency:**
  - Manual scraper execution as fallback
  - Alert admin via daily summary (no scraper activity)

**Risk 2: Job Lock Deadlocks**
- **Impact:** Jobs get stuck, scheduler stops processing
- **Mitigation:**
  - Redis lock TTL (locks expire automatically after 5 minutes)
  - Lock cleanup on process termination
  - Job lock monitoring (alert if locks held too long)
- **Contingency:**
  - Manual lock release via Redis CLI
  - Restart scheduler to reset locks

**Risk 3: Cache Invalidation Fails**
- **Impact:** Users see stale data
- **Mitigation:**
  - Cache invalidation is non-critical (cache miss is acceptable)
  - Retry failed invalidations (3 attempts)
  - Log cache invalidation errors for monitoring
- **Contingency:**
  - Manual cache flush via Redis CLI
  - Cache TTL ensures stale data expires eventually

**Risk 4: Scheduler Runs Too Frequently (Dev Mode in Production)**
- **Impact:** Excessive load on exchange websites, potential bot detection
- **Mitigation:**
  - Environment variable controls interval mode (prod vs dev)
  - Default to prod mode (safer intervals)
  - PM2 configuration explicitly sets SCRAPER_INTERVAL_MODE=prod
- **Contingency:**
  - Update .env to set SCRAPER_INTERVAL_MODE=prod
  - Restart scheduler
