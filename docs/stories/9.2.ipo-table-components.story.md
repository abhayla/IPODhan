## Story

**As a** frontend developer building the home page IPO tables,
**I want** four reusable, styled table components that display IPO data with proper color-coding and responsive layout,
**so that** users can view active and upcoming IPOs on the home page with clear visual indicators for IPO status and navigate to filtered dashboard views.

## Acceptance Criteria

1. Four distinct table components render correctly with proper data
2. Color-coding works based on date logic (green=open, yellow=closing soon, white=default)
3. Tables are responsive and match reference design
4. "More..." links navigate to dashboard with correct filters:
   - "More Mainline IPO..." → `/dashboard?category=mainboard`
   - "More SME IPO..." → `/dashboard?category=sme`
   - "More Upcoming Mainline IPO..." → `/dashboard?category=mainboard&status=upcoming`
   - "More Upcoming SME IPO..." → `/dashboard?category=sme&status=upcoming`
5. Tables follow existing design system and patterns
6. Loading states display properly
7. Accessibility: Tables have proper ARIA labels and semantic markup
8. Empty states handled gracefully with "No IPOs available" message

### Color-Coding Logic Context

**Reference Design** [Source: Epic 9 description]:
- Green background: IPO currently open (today between openDate and closeDate)
- Yellow background: IPO closing within 2 days (closeDate within 2 days from today)
- White/default: All other IPOs (upcoming or closed more than 2 days ago)

**Date Logic Implementation**:
```typescript
import { isWithinInterval, differenceInDays } from 'date-fns';

function getRowColorClass(ipo: IPO): string {
  const today = new Date();
  const openDate = new Date(ipo.dates.openDate);
  const closeDate = new Date(ipo.dates.closeDate);

  // Check if IPO is currently open
  const isOpen = isWithinInterval(today, {
    start: openDate,
    end: closeDate
  });

  if (isOpen) {
    return 'bg-green-50 hover:bg-green-100 border-l-4 border-green-500';
  }

  // Check if IPO is closing within 2 days
  const daysUntilClose = differenceInDays(closeDate, today);
  if (daysUntilClose >= 0 && daysUntilClose <= 2) {
    return 'bg-yellow-50 hover:bg-yellow-100 border-l-4 border-yellow-500';
  }

  // Default: white background
  return 'hover:bg-gray-50';
}
```

**Tailwind CSS Classes**:
- Green: `bg-green-50 hover:bg-green-100 border-l-4 border-green-500`
- Yellow: `bg-yellow-50 hover:bg-yellow-100 border-l-4 border-yellow-500`
- Default: `hover:bg-gray-50`

### Key Decisions & Rationale

**Decision 1: Use Basic Table Components vs DataTable**
- **Decision**: Use basic ui/table components instead of DataTable
- **Rationale**:
  - Home page needs lightweight, fast-loading components
  - No need for advanced features (sorting, searching, pagination)
  - Data pre-filtered and limited to 10 items per table
  - Simpler code, easier to maintain
  - Better performance (less JavaScript)

**Decision 2: Color-Coding Implementation**
- **Decision**: Implement color-coding in row className using helper function
- **Rationale**:
  - Tailwind CSS classes for styling (consistent with design system)
  - date-fns library for date calculations (accurate and tested)
  - Helper function for reusability and testability
  - No state management needed (pure function based on props)

**Decision 3: Separate Components vs Single Generic Component**
- **Decision**: Create two separate components (IPOListTable, UpcomingIPOTable)
- **Rationale**:
  - Different column structures (3 columns each, but different headers)
  - Different rendering logic (status text in upcoming table)
  - Easier to test and maintain separately
  - Clearer code, less conditional logic
  - Follows single responsibility principle

**Decision 4: Props-Based Configuration**
- **Decision**: Components receive all data as props, no internal data fetching
- **Rationale**:
  - Aligns with React best practices (dumb/presentational components)
  - Server-side data fetching in page component (better for SEO)
  - Easier to test (just pass mock data as props)
  - Reusable components (could be used elsewhere with different data)

**Decision 5: Loading State Implementation**
- **Decision**: Use skeleton component for loading state
- **Rationale**:
  - Better UX than spinner (shows structure of content)
  - Prevents layout shift (skeleton matches actual table dimensions)
  - Follows modern web design patterns
  - Tailwind's animate-pulse provides smooth loading animation
