## Challenges & Solutions

### Challenge 1: TypeScript Path Aliases and Environment Loading
**Problem:** When importing `db` from `@/lib/db/index`, the module initializes and creates a Pool immediately, BEFORE the seed script's `dotenv.config()` runs. This caused "client password must be a string" error.

**Attempted Solutions:**
1. ❌ URL-encoding password in DATABASE_URL
2. ❌ Explicit String() casting in Pool config
3. ❌ Moving dotenv.config() to top of seed-data.ts

**Final Solution:** ✅ Created wrapper script (seed.js) that:
- Loads .env.local using Node.js require('dotenv')
- THEN executes seed-data.ts via tsx
- Environment variables available before any TS modules load

**Lesson Learned:** Module-level initialization code runs at import time. When using TypeScript path aliases with tsx, imports execute before top-level script code.

### Challenge 2: Database Connection with Special Characters
**Problem:** Password contains @ symbol, which is also the delimiter in DATABASE_URL between credentials and host.

**Solution:** Modified db/index.ts to check for DATABASE_HOST and use individual parameters instead of connectionString when available. This avoids URL parsing entirely.

### Challenge 3: Redis Not Available Locally
**Problem:** Seed script uses repositories that expect Redis client, but Redis may not be running during development.

**Solution:** Wrapped getRedisClient() in try-catch, create mock Redis client with stub methods if connection fails. Script proceeds without caching.

## Lessons Learned

1. **Environment Variable Loading Order Matters**
   - Module-level code executes at import time
   - TypeScript path aliases add complexity to execution order
   - Wrapper scripts provide clean solution for initialization order

2. **URL Encoding vs Individual Parameters**
   - Special characters in connection strings are problematic
   - Individual connection parameters are more robust
   - Supporting both approaches provides flexibility

3. **Graceful Degradation is Valuable**
   - Optional dependencies (like Redis) shouldn't block critical operations
   - Mock objects enable testing without full infrastructure
   - Clear logging helps users understand what's running/missing

4. **Realistic Data Improves Testing**
   - Using actual Indian company conventions makes demo more believable
   - Real sector names, registrars, and holidays provide better context
   - Varied scenarios (UPCOMING/OPEN/CLOSED/LISTED) enable comprehensive testing
