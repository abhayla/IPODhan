# Story 9.7a: Mainboard IPO Performance Tracker Page

## Status
Ready (PO Approved - v1.1)

## Story

**As a** investor interested in Mainboard IPO post-listing performance,
**I want** to view a comprehensive performance tracker showing listing day gains and current profit/loss for Mainboard IPOs,
**so that** I can analyze how Mainboard IPOs have performed since listing, identify successful listings, and make informed investment decisions based on historical performance data.

## Acceptance Criteria

1. Mainboard Performance tracker page accessible at `/mainboard-ipo-performance-tracker`
2. Table displays all 7 columns with correct Mainboard IPO data only
3. Year filter works correctly (default: current year)
4. Year filter updates URL query params
5. Only Mainboard IPOs displayed (category=MAINBOARD filter applied)
6. Color coding applied correctly:
   - Green for positive percentages
   - Red for negative percentages
7. "IPO Detail" links navigate to respective IPO detail pages
8. "Stock Quotes" links functional (external or internal)
9. Calculations are accurate:
   - Listing Day Gain = ((listingClose - issuePrice) / issuePrice) × 100
   - Profit/Loss = ((currentPrice - issuePrice) / issuePrice) × 100
10. IPOs sorted by listing date (descending)
11. Page uses ISR with 5-minute revalidation
12. Responsive: table on desktop, compact cards on mobile
13. Empty state shows "No Mainboard IPOs listed in [year]" message
14. Loading skeleton displays during data fetch
15. SEO metadata configured (title, description, keywords)
16. Navigation link added to "Mainboard IPOs" submenu
17. Performance data displays with 2 decimal precision for percentages
18. Rupee symbol (₹) displayed correctly for prices

    const performanceData = response.data.map((ipo) => {
      const issuePrice = ipo.issuePrice || ipo.priceRangeMax;
      const listingClose = ipo.listingPerformance?.listingPrice || 0;
      const currentPrice = ipo.listingPerformance?.currentPrice || null;

      const listingDayGain = issuePrice > 0
        ? ((listingClose - issuePrice) / issuePrice) * 100
        : 0;

      const currentGain = currentPrice && issuePrice > 0
        ? ((currentPrice - issuePrice) / issuePrice) * 100
        : null;

      return {
        ipo,
        performance: ipo.listingPerformance,
        listingDayGain: Number(listingDayGain.toFixed(2)),
        currentGain: currentGain ? Number(currentGain.toFixed(2)) : null
      };
    });

### ISR Configuration

**Incremental Static Regeneration** [Source: Story 9.4]:
- Enable with: `export const revalidate = 300;` (5 minutes)
- How it works:
  1. Page generated statically at build time
  2. First request serves cached page (instant)
  3. After 5 minutes, next request triggers background regeneration
  4. Stale page served while regenerating
  5. New page cached and served to subsequent requests
- Benefits:
  - Fast page loads (static serving)
  - Fresh data (5-minute updates for current prices)
  - Low server load (caching)
  - SEO-friendly (static HTML)

**Cache Headers**:
- Next.js automatically sets cache headers
- Verify in browser: `cache-control: s-maxage=300, stale-while-revalidate`

### Technical Decisions

**Decision 1: Server Component for Page**
- **Decision**: Use async server component for page
- **Rationale**:
  - Better SEO (data in initial HTML)
  - Faster page load (no client-side fetching)
  - Reduced JavaScript bundle
  - ISR works seamlessly with server components
  - Performance data is not real-time (5-minute ISR is acceptable)

**Decision 2: Client Component Only for Year Filter**
- **Decision**: Year filter is client component, table is server component
- **Rationale**:
  - Year filter requires interactivity (onChange, router.push)
  - Table is pure presentation (except expandable links)
  - Minimize client JavaScript
  - Only interactive parts need 'use client'

**Decision 3: URL State for Year Persistence**
- **Decision**: Use URL query params for year state (`?year=2024`)
- **Rationale**:
  - Shareable URLs (users can bookmark specific year)
  - Browser back/forward works correctly
  - Server can read state (no client-side hydration mismatch)
  - SEO-friendly (different URLs for different years)

**Decision 4: Calculations on Service Layer**
- **Decision**: Calculate listing day gain and current gain in service layer
- **Rationale**:
  - Keep components presentational (display only)
  - Calculations can be unit tested separately
  - Easier to maintain calculation logic
  - Consistent calculation across app

**Decision 5: Expandable Links for Company Name**
- **Decision**: Use expandable/collapsible links instead of always-visible links
- **Rationale**:
  - Reduces visual clutter in table
  - Matches Epic 9 specification (Story 9.7a)
  - Better mobile experience (less crowded)
  - User can expand only when needed

**Decision 6: 5-Minute ISR for Current Prices**
- **Decision**: Use 5-minute ISR revalidation for current prices
- **Rationale**:
  - Balance freshness and performance
  - Current prices don't need real-time updates for performance tracking
  - Reduces API/database load
  - Matches other pages in Epic 9 (consistent approach)
  - Future enhancement: WebSocket for real-time updates if needed

**Decision 7: Graceful Degradation on Missing Current Price**
- **Decision**: Show '-' (dash) if current price is not available
- **Rationale**:
  - Some IPOs may not have current price data yet
  - Better UX than showing error
  - Indicates data is not available (clear to user)
  - Page still functional with partial data
