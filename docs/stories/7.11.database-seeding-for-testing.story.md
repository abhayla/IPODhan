## Story
**As a** IPODhan QA engineer,
**I want** a database seeding mechanism that populates at least 150 IPO records with diverse statuses and realistic data,
**so that** I can perform comprehensive testing across all application features without being blocked by insufficient test data.

## Acceptance Criteria

1. Database contains at least 150 IPO records after seeding
2. IPO records include diverse statuses: OPEN (10-15%), CLOSED (20-25%), LISTED (50-60%), UPCOMING (10-15%)
3. All required schema fields are properly populated according to `web/lib/db/schema.ts` constraints
4. Seeded IPOs have unique slugs (no duplicates)
5. Category distribution: MAINBOARD (70%), SME (30%)
6. All enum values are valid (category, status, exchange) per schema definitions
7. Historical data fields populated where applicable (listing performance for LISTED IPOs)
8. Seed script can be executed via CLI: `npm run seed:database`
9. Seed script is idempotent (can run multiple times without creating duplicates)
10. Seed script handles Drizzle ORM schema defaults properly (createdAt, updatedAt)
11. Seed script uses proper field names: `priceRangeMin`/`priceRangeMax` (not priceBandLow/High)
12. Seed script logs progress and completion status with structured logging

### Technical Investigation Summary

**Failed Seed Attempts:**

1. **seed-historical-ipos.ts**
   - Issue: Used `priceBandLow`/`priceBandHigh` instead of `priceRangeMin`/`priceRangeMax`
   - Issue: Missing `createdAt`/`updatedAt` explicit values
   - Result: All inserts failed

2. **seed-direct-historical-ipos.ts**
   - Issue: Same field name mismatches
   - Issue: Drizzle ORM not handling schema defaults properly
   - Result: All inserts failed

3. **seed-historical-fixed.ts**
   - Issue: Database constraints preventing inserts with nullable required fields
   - Issue: Fuzzy matching incorrectly matching all 480 IPOs to existing 28
   - Result: All inserts failed

**Root Causes:**
1. Schema field name mismatches (priceBandLow vs priceRangeMin)
2. Drizzle ORM requires explicit timestamps despite schema defaults
3. Nullable field handling inconsistencies
4. Fuzzy matching algorithm too aggressive (100% match rate suspicious)

### Schema Field Reference

**Critical Fields (from web/lib/db/schema.ts):**

```typescript
// Required fields (notNull)
companyName: varchar('company_name', { length: 255 }).notNull()
slug: varchar('slug', { length: 255 }).notNull().unique()
category: ipoCategoryEnum('category').notNull()
status: ipoStatusEnum('status').notNull()
createdAt: timestamp('created_at').defaultNow().notNull()
updatedAt: timestamp('updated_at').defaultNow().notNull()

// Correct field names (NOT priceBandLow/High)
priceRangeMin: integer('price_range_min')  // min price per share
priceRangeMax: integer('price_range_max')  // max price per share

// Optional fields (nullable)
sector: varchar('sector', { length: 100 })
issueSize: numeric('issue_size', { precision: 10, scale: 2 })
lotSize: integer('lot_size')
openDate: date('open_date')
closeDate: date('close_date')
allotmentDate: date('allotment_date')
listingDate: date('listing_date')
```

**Enum Values:**
- `category`: MAINBOARD, SME, RIGHTS, NCD, FPO
- `status`: UPCOMING, OPEN, CLOSED, LISTED
- `exchange`: NSE, BSE, BOTH

### Error Handling Strategy

**Duplicate Detection:**

- Use upsert pattern for specific conflict handling

**Validation Failures:**
- Pre-validate data before insert (check enums, required fields)
- Log validation errors with data sample
- Skip invalid records
- Continue with valid records

```sql
SELECT slug, COUNT(*) FROM ipos GROUP BY slug HAVING COUNT(*) > 1;

-- Listing performance coverage
SELECT
  COUNT(DISTINCT i.id) as listed_ipos,
  COUNT(DISTINCT lp.id) as with_performance,
  ROUND(100.0 * COUNT(DISTINCT lp.id) / COUNT(DISTINCT i.id), 2) as coverage_percent

WHERE i.status = 'LISTED';
```
