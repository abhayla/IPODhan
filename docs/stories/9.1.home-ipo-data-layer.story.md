## Story

**As a** developer preparing the home page for IPO table display,
**I want** a specialized data fetching service layer that provides filtered IPO data for four table categories,
**so that** the home page can efficiently retrieve and cache active mainboard, SME, and upcoming IPO data for display to users.

## Acceptance Criteria

1. Four data fetching functions return properly typed IPO data
2. Each function fetches correct category and status combinations
3. Results are limited to 10 items per table
4. Data is cached in Redis with proper cache keys
5. Functions handle API errors without throwing
6. All existing API functionality continues to work unchanged

### Caching Strategy Context

**Cache-Aside Pattern** [Source: existing implementation in ipo-repository.ts]:
1. Check Redis for cached data using cache key
2. If cache hit: Parse JSON and return
3. If cache miss: Fetch from database
4. Store result in Redis with TTL
5. Return data to caller

**Cache TTL Values** [Source: web/lib/cache/cache-keys.ts]:
- IPO List: 300 seconds (5 minutes)
- IPO Detail: 300 seconds (5 minutes)
- Historical IPOs: 600 seconds (10 minutes)

**Cache Key Pattern**:
- Descriptive namespace: `home:mainboard:ipos`
- Use colons `:` as separators
- Keep keys short and meaningful

**Redis Client Access** [Source: web/lib/cache/redis-client.ts]:
- Import Redis client from `web/lib/cache/redis-client.ts`
- Use `redis.get(key)` to retrieve cached data
- Use `redis.setex(key, ttl, value)` to store with expiration
- Handle Redis errors gracefully (cache is optional, not critical)

### Performance Considerations

**Caching Benefits**:
- Reduces database load (PostgreSQL queries expensive)
- Faster page load times (Redis sub-millisecond latency)
- Home page is high-traffic (cache critical for performance)

**Cache Invalidation**:
- Not needed for Story 9.1 (5-minute TTL is sufficient)
- Scraper updates IPO data → cache expires after 5 minutes
- Future: Implement explicit cache invalidation on data updates

**Query Optimization**:
- Limit results to 10 items (LIMIT 10 in SQL)
- Use indexed columns for filtering (status, category, closeDate, openDate)
- Sort by date columns (already indexed)
- Avoid complex joins (not needed for home page tables)

### Key Decisions & Rationale

**Decision 1: Service Layer vs Direct Repository Calls**
- **Decision**: Create dedicated service layer for home page data
- **Rationale**:
  - Separates concerns (home page logic separate from repository)
  - Easier to test and maintain
  - Allows home-specific caching strategy
  - Prevents home page from directly depending on repository

**Decision 2: Return Empty Array on Error vs Throw**
- **Decision**: Return empty array `[]` on any error
- **Rationale**:
  - Home page should always render (graceful degradation)
  - Empty tables better than error page for users
  - Errors logged for debugging but don't block rendering
  - Aligns with "fail silently" UX pattern for non-critical data

**Decision 3: 5-Minute Cache TTL**
- **Decision**: Cache data for 5 minutes (300 seconds)
- **Rationale**:
  - Balance between freshness and performance
  - IPO data doesn't change frequently (updates every 15-30 minutes from scraper)
  - Home page is high-traffic (cache reduces database load significantly)
  - Acceptable staleness for home page display

**Decision 4: Separate Functions vs Single Function with Parameters**
- **Decision**: Create four separate functions instead of one with parameters
- **Rationale**:
  - Clearer API for consumers (no need to remember parameter combinations)
  - Easier to test each function independently
  - Allows different cache keys for each data set
  - Follows single responsibility principle
