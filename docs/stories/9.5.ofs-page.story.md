**Migration SQL**:
```sql
-- Add OFS category to ipo_category enum if it doesn't exist
DO $$
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM pg_enum
    WHERE enumlabel = 'OFS'
    AND enumtypid = (SELECT oid FROM pg_type WHERE typname = 'ipo_category')
  ) THEN
    ALTER TYPE ipo_category ADD VALUE 'OFS';
  END IF;
END $$;
```

### Key Decisions & Rationale

**Decision 1: Schema Enhancement (OFS Category)**
- **Decision**: Add 'OFS' to ipoCategoryEnum in database schema
- **Rationale**:
  - OFS was missing from enum
  - Required for proper category filtering
  - Idempotent migration ensures safe deployment
  - Backward compatible (doesn't affect existing data)

**Decision 2: Temporary Field Mapping**
- **Decision**: Use temporary mapping (nonRetailDate → openDate, retailDate → closeDate)
- **Rationale**:
  - Schema doesn't have dedicated fields yet
  - Semantics align with OFS bidding schedule
  - Easy to update when schema is enhanced
  - Isolated to single function (transformOFSData)

**Decision 3: DataTable Component Reuse**
- **Decision**: Use existing DataTable component instead of creating new table
- **Rationale**:
  - DRY principle (Don't Repeat Yourself)
  - Tested, production-ready component
  - Consistent UX across all pages
  - Reduced development time and maintenance

**Decision 4: Educational Banner**
- **Decision**: Add educational banner explaining OFS concept
- **Rationale**:
  - OFS is less familiar than IPO to retail investors
  - Two-day bidding schedule needs explanation
  - Helps users understand Non-Retail vs Retail dates
  - Improves user experience and informed decision-making

**Decision 5: Single Table View (No Tabs)**
- **Decision**: Single table view instead of tabs (unlike Rights Issues page)
- **Rationale**:
  - OFS doesn't have clear "Upcoming" vs "Live" distinction
  - Simpler UX for investors
  - Easier to scan all OFS opportunities at once
  - Follows Epic 9 specifications
