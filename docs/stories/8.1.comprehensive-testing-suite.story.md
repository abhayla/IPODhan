## Story
**As a** development team and QA engineer,
**I want** comprehensive testing coverage across all application layers (unit, integration, E2E, load testing) with >85% code coverage and automated cross-browser testing,
**so that** we can ensure all features work correctly, catch bugs before production, verify performance targets are met, and maintain high code quality throughout the application lifecycle.

## Acceptance Criteria
1. All repository layer classes have unit tests with >90% code coverage using Vitest with mocked database
2. All API routes have integration tests with >85% code coverage using Vitest with real PostgreSQL and Redis test containers
3. E2E test suite (Playwright) covers 5 critical user journeys: (1) Browse IPOs with filters, (2) Search IPOs, (3) View IPO detail page, (4) Use lot calculator, (5) Compare IPOs
4. E2E tests run successfully on Chrome, Firefox, and Edge browsers
5. Mobile responsive E2E tests validate critical flows on simulated mobile viewports (iOS Safari, Android Chrome)
6. Load testing suite (Artillery or k6) simulates 1000 concurrent users with p95 response time <500ms
7. All tests passing with zero failures in CI/CD pipeline
8. Test coverage report generated and accessible (HTML report)
9. No console errors in production build verified by E2E tests
10. Cross-browser testing validates UI consistency across major browsers
11. Performance benchmarks documented: API response times, page load times, database query times
12. Test documentation created: how to run tests, add new tests, interpret results

    ```typescript
    import { PostgreSqlContainer } from '@testcontainers/postgresql';
    import { GenericContainer } from 'testcontainers';
    import { drizzle } from 'drizzle-orm/node-postgres';
    import { migrate } from 'drizzle-orm/node-postgres/migrator';
    import { Pool } from 'pg';

    let postgresContainer: PostgreSqlContainer;
    let redisContainer: GenericContainer;
    let dbPool: Pool;

    export async function setupTestDatabase() {
      // Start PostgreSQL container
      postgresContainer = await new PostgreSqlContainer('postgres:16')
        .withDatabase('ipodhan_test')
        .start();

      // Start Redis container
      redisContainer = await new GenericContainer('redis:7.2-alpine')
        .withExposedPorts(6379)
        .start();

      // Create connection pool
      dbPool = new Pool({
        connectionString: postgresContainer.getConnectionUri(),
      });

      // Run migrations
      const db = drizzle(dbPool);
      await migrate(db, { migrationsFolder: './db/migrations' });

      return {
        dbUrl: postgresContainer.getConnectionUri(),
        redisUrl: `redis://${redisContainer.getHost()}:${redisContainer.getMappedPort(6379)}`,
        db,
        pool: dbPool,
      };
    }

    export async function teardownTestDatabase() {
      await dbPool?.end();
      await postgresContainer?.stop();
      await redisContainer?.stop();
    }
    ```

### Coding Standards

**Source:** [docs/architecture/coding-standards.md]

**Test Naming Conventions:**
- Test files: `{module-name}.test.ts` or `{feature}.spec.ts`
- Test suites: `describe('FeatureName', () => { ... })`
- Test cases: `test('should do something when condition', async () => { ... })`

**Test Structure (AAA Pattern):**
```typescript
test('should return IPOs filtered by status', async () => {
  // Arrange: Set up test data and mocks
  const testIPO = { slug: 'test-ipo', status: 'OPEN', ... };
  await db.insert(ipos).values(testIPO);

  // Act: Execute the code under test
  const response = await fetch('/api/ipos?status=OPEN');
  const data = await response.json();

  // Assert: Verify expected outcomes
  expect(response.status).toBe(200);
  expect(data.data).toHaveLength(1);
  expect(data.data[0].slug).toBe('test-ipo');
});
```

**Test Best Practices:**
- One assertion per test (when possible)
- Descriptive test names (what, when, expected)
- Mock external dependencies (APIs, file system)
- Clean up after tests (database, Redis)
- Use test factories for complex data
- Avoid hardcoded values (use variables/constants)

### Risks and Mitigation

**Source:** Epic 8

**Risk 1: Tests take too long to run**
- **Impact:** Slow feedback loop, developers skip tests
- **Mitigation:**
  - Run unit tests in parallel (Vitest default)
  - Use test containers for isolation (fast setup)
  - Run E2E tests on critical paths only
  - Cache dependencies in CI/CD
- **Contingency:**
  - Split test suite into fast/slow suites
  - Run E2E tests nightly instead of per-commit

**Risk 2: Flaky E2E tests**
- **Impact:** False failures, loss of trust in tests
- **Mitigation:**
  - Use Playwright auto-wait (no manual sleeps)
  - Set explicit wait conditions
  - Use stable test data (no randomness)
  - Retry failed tests (max 2 retries in CI)
- **Contingency:**
  - Isolate flaky tests, investigate root cause
  - Temporarily disable flaky tests, file issue

**Risk 3: Low test coverage**
- **Impact:** Bugs slip through, low confidence in releases
- **Mitigation:**
  - Set coverage thresholds in CI (fail build if below)
  - Review coverage reports in PRs
  - Prioritize testing critical paths
  - Add tests for bug fixes (regression tests)
- **Contingency:**
  - Gradually increase coverage over time
  - Focus on high-risk areas first

**Risk 4: Load tests don't match production**
- **Impact:** Performance issues in production
- **Mitigation:**
  - Use realistic traffic patterns
  - Test on production-like infrastructure
  - Monitor production metrics for comparison
  - Run load tests before major releases
- **Contingency:**
  - Add production monitoring (Sentry, PM2)
  - Scale infrastructure if needed (more PM2 instances)
