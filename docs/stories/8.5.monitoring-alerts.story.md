## Story
**As a** platform administrator managing IPODhan in production,
**I want** proactive monitoring and alerting configured for site health, errors, scraper status, and performance metrics,
**so that** I can detect and resolve issues before users report them, ensuring 99.5%+ uptime and reliable service.

## Acceptance Criteria
1. UptimeRobot monitoring active with `/api/health` checked every 5 minutes
2. Health check endpoint responding correctly with database and Redis status
3. Error tracking configured (Sentry if used, or alternative approach)
4. Google Analytics 4 tracking pageviews, events, and Core Web Vitals
5. PM2 logs accessible and rotating properly (daily, keep 7 days)
6. Alert test completed: Manually trigger alert and verify delivery (email or notification)
7. Alerting rules configured for critical events:
   - Site down for 3+ consecutive checks (5 min = 3 checks)
   - Error rate >5%
   - Scraper failed 3+ consecutive runs
   - Memory usage >90%
8. Structured logging implemented with Pino for both web and scraper
9. Scraper logs stored in database table with status tracking
10. PM2 web dashboard or monitoring interface accessible for CPU/memory/restart metrics

    ```typescript
    import { db } from '@/lib/db';
    import { redis } from '@/lib/redis';

    export async function GET() {
      const checks = {
        database: 'unknown',
        redis: 'unknown'
      };

      try {
        // Test database connection
        await db.execute('SELECT 1');
        checks.database = 'healthy';
      } catch (error) {
        checks.database = 'unhealthy';
      }

      try {
        // Test Redis connection
        await redis.ping();
        checks.redis = 'healthy';
      } catch (error) {
        checks.redis = 'unhealthy';
      }

      const allHealthy = checks.database === 'healthy' && checks.redis === 'healthy';

      return Response.json({
        status: allHealthy ? 'healthy' : 'unhealthy',
        timestamp: new Date().toISOString(),
        services: checks
      }, {
        status: allHealthy ? 200 : 503
      });
    }
    ```

### Architecture Context
This story implements comprehensive monitoring and alerting for the IPODhan production environment. The monitoring stack ensures proactive detection of issues before users report them, targeting 99.5%+ uptime.

[Source: docs/epics/epic-8-sharded.md, architecture/monitoring-and-observability.md]

### Monitoring Stack Overview

**Components:**
1. **UptimeRobot** - External uptime monitoring (checks `/api/health` every 5 minutes)
2. **Sentry** (Optional) - Error tracking and performance monitoring
3. **Google Analytics 4** - User behavior, pageviews, Core Web Vitals
4. **PM2** - Application metrics (CPU, memory, restarts)
5. **Pino** - Structured logging (JSON format)
6. **Custom Database Logging** - Scraper run tracking

[Source: architecture/monitoring-and-observability.md#monitoring-stack]

### Health Check Endpoint Specification

The health check endpoint must:
- Respond at `/api/health`
- Return 200 status when all services healthy
- Return 503 status when any service unhealthy
- Test database connectivity (execute simple query)
- Test Redis connectivity (ping command)
- Return JSON response format:
```json
{
  "status": "healthy",
  "timestamp": "2025-10-08T10:30:00Z",
  "services": {
    "database": "healthy",
    "redis": "healthy"
  }
}
```

[Source: architecture/monitoring-and-observability.md#health-check-endpoint]

- Monitor Type: HTTP(s)

- Interval: 5 minutes

### Alerting Rules and Thresholds

**Critical Alerts (Immediate Action Required):**
1. **Site Down** - Health check fails 3 consecutive times (15 minutes)
   - Tool: UptimeRobot
   - Action: Email + SMS notification

2. **Error Rate >5%** - High error rate over 10-minute window
   - Tool: Sentry or custom log analysis
   - Action: Email notification

3. **Scraper Failed 3+ Times** - 3 consecutive scraper failures
   - Tool: Custom database monitoring
   - Action: Email notification

4. **Memory Usage >90%** - App approaching memory limit
   - Tool: PM2 monitoring or custom script
   - Action: Email notification

**Warning Alerts (Monitor Closely):**
- Database query performance degradation
- Cache hit rate drops below 80%
- Disk space below 20%

[Source: architecture/monitoring-and-observability.md#alerting]
