## Story
**As a** IPODhan platform administrator,
**I want** the IPO Alerts API integrated as a fallback data source when NSE/BSE scraping fails,
**so that** the platform continues to display fresh IPO data even during scraper failures, ensuring 95%+ data availability and maintaining user trust through reliable information delivery.

## Acceptance Criteria
1. IPO Alerts API client is implemented with proper authentication and request handling
2. API client fetches IPO data from IPO Alerts endpoints: `/ipos?status=open`, `/ipos?status=upcoming`, `/ipos/{id}`
3. API response data is validated using Zod schemas and transformed to match IPODhan data models
4. Fallback logic triggers automatically when NSE or BSE scraper fails 3+ consecutive times
5. Fallback scraper upserts IPO data to PostgreSQL database via IPORepository (merge with existing NSE/BSE data)
6. Fallback scraper creates subscription snapshots via SubscriptionRepository with source attribution
7. Fallback scraper invalidates relevant Redis cache keys after successful data update
8. Fallback scraper logs all operations with structured logging (API calls, success, failures, rate limits)
9. Rate limiting is implemented: 100 requests/hour limit with request tracking and throttling
10. Fallback scraper handles API errors gracefully (404, 429, 500) with exponential backoff
11. Fallback scraper can be executed manually via CLI for testing: `npm run start:fallback`
12. Scraper orchestrator (Story 7.4) can invoke fallback automatically when primary scrapers fail

1. Scraper file (core logic): Fetch/scrape data, validate, transform
2. Orchestrator file (workflow): Call scraper, persist data, invalidate cache, handle errors
3. CLI invokes orchestrator based on --source flag

```javascript
async function fallbackScrape() {
  try {
    // 1. Check rate limit
    if (!rateLimiter.canMakeRequest()) {
      logger.warn('Rate limit reached, skipping API fallback');
      return;
    }

    // 2. Fetch from API
    const response = await fetch(IPO_ALERTS_API_URL);
    const ipos = await response.json();

    // 3. Validate with Zod
    const validated = IPOSchema.parse(ipos);

    // 4. Upsert to database (merge with existing NSE/BSE data)
    await IPORepository.upsert(validated);

    // 5. Invalidate cache
    await invalidateCache('ipos');

    // 6. Log success
    logger.info({ count: ipos.length, source: 'IPO_ALERTS_API' }, 'API fallback successful');

  } catch (error) {
    logger.error({ error }, 'API fallback failed');
    // No further fallback available
  }
}
```

**Cache Invalidation Strategy:**
Same as Story 7.1 and 7.2:
1. Delete cache keys:
   - `ipos:list:*` (all listing variations)
   - `ipo:{slug}` (specific IPO if updated)
   - `subscription:latest:{slug}` (if subscription changed)
2. Set "Last Updated" timestamp in database (Story 7.4)

**Data Merge Logic for API Fallback:**

**Guiding Principle:** NSE/BSE scrapers are the authoritative source. API fallback is supplementary and should NOT overwrite existing data.

**Merge Behavior:**
1. **If IPO does NOT exist in database:**
   - Create new IPO from API data
   - Set all fields from API response
   - Track source: `source='IPO_ALERTS_API'`
   - Log: "New IPO {slug} created from API fallback"

2. **If IPO EXISTS in database (scraped by NSE/BSE):**
   - **DO NOT OVERWRITE these fields** (NSE/BSE data is authoritative):
     - `companyName`, `slug`, `category`, `sector`
     - `issueSize`, `priceRange` (min/max)
     - `lotSize`, `faceValue`
     - `dates` (openDate, closeDate, allotmentDate, listingDate)
     - `companyDescription`
     - `registrar`, `leadManagers`
     - `rating`, `ratingRationale`
   - **DO MERGE these fields** (additive, not replacement):
     - `listingExchanges`: Add API exchange if different (e.g., API says "BSE", existing has ["NSE"] → update to ["NSE", "BSE"])
     - `source` metadata: Add 'IPO_ALERTS_API' to sources list (if schema supports tracking multiple sources)
   - **Log data discrepancies** (for monitoring data quality):
     - If API data differs from NSE/BSE data: log warning
     - Example: "API reports issueSize: 500 crores, NSE reports: 450 crores (NSE data retained)"
   - **Update `updatedAt` timestamp** to reflect latest data check
   - Log: "IPO {slug} already exists with NSE/BSE data, API fallback data not merged (NSE/BSE authoritative)"

3. **Subscription Data Merge:**
   - If IPO exists with NSE/BSE subscription data: Create new subscription snapshot from API (time-series data)
   - If IPO does not have subscription data: Create subscription snapshot from API
   - Always create new snapshot, never update existing (subscription data is time-series)
   - Track source: `source='IPO_ALERTS_API'` in subscription metadata

**Rationale:**
- NSE/BSE scrapers scrape official exchange data (most accurate)
- API fallback may have outdated or less accurate data
- Overwriting NSE/BSE data with API data would reduce data quality
- API fallback is primarily for filling gaps when scrapers fail, not for improving existing data

### Error Handling Strategy

**Source:** [docs/architecture/error-handling-strategy.md] and Epic 7

**API Fallback Error Handling:**
1. **API Request Failures:**
   - **404 (Not Found):** Log warning, return empty result
   - **429 (Rate Limit Exceeded):** Log error, throw `RateLimitExceededError`, do not retry
   - **500/502/503 (Server Error):** Log error, retry 3 times with exponential backoff
   - **Network Errors:** Log error, retry 3 times with exponential backoff
   - **Timeout:** Log error (timeout after 30s), retry 3 times
   - **401 (Unauthorized):** Log error, check API key configuration, do not retry

2. **Data Transformation Failures:**
   - Log error with API response sample (redact sensitive info)
   - Skip invalid IPO (do not insert to database)
   - Continue processing other IPOs
   - Track transformation failure count in logs

3. **Validation Failures:**
   - Log validation error with data sample (redact sensitive info)
   - Skip invalid IPO (do not insert to database)
   - Continue processing other IPOs
   - Track validation failure count in logs

4. **Database Failures:**
   - Retry 3 times with exponential backoff
   - Log error with query context
   - If all retries fail: skip this IPO, log failure
   - Continue processing other IPOs

5. **Cache Invalidation Failures:**
   - Log error
   - Do NOT crash scraper (cache miss is acceptable)
   - Continue processing

6. **Rate Limit Enforcement:**
   - Check rate limit BEFORE API call
   - If limit reached: log error, throw `RateLimitExceededError`
   - Do not retry until rate limit window resets (1 hour)

**Error Logging Format (Pino):**
```typescript
logger.error({
  error: error.message,
  stack: error.stack,
  context: { url, statusCode, attempt, duration, source: 'IPO_ALERTS_API' },
  timestamp: new Date().toISOString()
}, 'API fallback failed');
```

### Performance Considerations

**Source:** Epic 7

**Performance Targets:**
- Scraper execution time: <30 seconds for typical API response (10-20 IPOs)
- API request time: <5 seconds per request
- Database upsert time: <100ms per IPO
- Cache invalidation time: <50ms
- Transformation time: <10ms per IPO

**Optimization Strategies:**
- **Native Fetch:** Use built-in fetch API (no axios dependency, faster)
- **Parallel Processing:** Process multiple IPOs in parallel (use `Promise.all()` for upserts)
- **Connection Pooling:** Reuse database connections (Drizzle ORM handles this)
- **Redis Pipelining:** Batch cache invalidation commands (use `redis.pipeline()`)
- **Efficient Validation:** Zod validation is fast, but minimize unnecessary validations

**Resource Management:**
- No browser overhead (fetch API only)
- Minimal memory usage (no Puppeteer instances)
- API client reuses connections (keep-alive)
- Rate limiter uses in-memory tracking (lightweight)

### Risks and Mitigation

**Source:** Epic 7

**Risk 1: IPO Alerts API Downtime**
- **Impact:** Fallback scraper fails, no new data when NSE/BSE also fail
- **Mitigation:**
  - Log all API failures for monitoring
  - Implement retry logic (3 attempts)
  - Story 7.5 will add monitoring alerts
- **Contingency:**
  - Display last known data with "Last updated: X hours ago"
  - Manual seed data updates as last resort
  - No further fallback available (API is final fallback)

**Risk 2: Rate Limit Exceeded**
- **Impact:** API requests rejected, fallback scraper fails
- **Mitigation:**
  - Implement rate limiting (100 requests/hour)
  - Log warnings at 80% threshold
  - Track request timestamps in-memory
- **Contingency:**
  - Wait until rate limit resets (1 hour)
  - Reduce scraper frequency if hitting limits frequently
  - Upgrade API plan if available (higher limits)

**Risk 3: API Response Format Changes**
- **Impact:** Zod validation fails, no data extracted from API
- **Mitigation:**
  - Use flexible Zod schemas (optional fields where applicable)
  - Log API response samples for debugging
  - Add snapshot testing for API response structure
- **Contingency:**
  - Update Zod schemas within 24 hours (schema evolution)
  - Contact API provider for advance notice of breaking changes

**Risk 4: API Data Quality Issues**
- **Impact:** API provides inaccurate or outdated IPO data
- **Mitigation:**
  - API fallback does NOT overwrite NSE/BSE data (less authoritative)
  - Log data discrepancies between API and NSE/BSE
  - Add source attribution on frontend ("Data from IPO Alerts API")
- **Contingency:**
  - Rely on NSE/BSE data as primary (fallback is supplementary)
  - User feedback mechanism for data issues (Phase 2)

**Risk 5: API Authentication Failures**
- **Impact:** API rejects requests (401 Unauthorized), fallback fails
- **Mitigation:**
  - Verify API key configuration in `.env`
  - Test API authentication during development
  - Log authentication errors clearly
- **Contingency:**
  - Contact API provider to verify API key
  - Regenerate API key if compromised
  - Check if API requires IP whitelisting
