### Repository Layer Architecture
**Source:** `docs/architecture.md` lines 753-764, 1058-1073

**Architectural Pattern:** Repository Pattern (Data Access Layer)

**Responsibility:** Abstract database queries and caching logic behind clean interfaces, enabling:
- Testability with mock data
- Future database migration flexibility
- Clean separation of business logic from data access
- Centralized caching logic

**Key Repository Interfaces Required:**

**IPORepository:**
- `findAll(filters)` - Query IPOs with filters/pagination
- `findBySlug(slug)` - Get IPO by slug with relations
- `findById(id)` - Get IPO by ID
- `search(query)` - Fuzzy search by company name
- `create(ipo)` - Create new IPO
- `update(id, data)` - Update IPO

**SubscriptionRepository:**
- `findByIPO(ipoId)` - Get subscription history
- `findLatest(ipoId)` - Get latest snapshot
- `createSnapshot(ipoId, data)` - Insert new subscription data

**GMPRepository:**
- `findByIPO(ipoId, days)` - Get GMP history with date range
- `findLatest(ipoId)` - Get latest GMP record
- `create(ipoId, gmpData)` - Insert new GMP record

**FinancialDataRepository:**
- `findByIPO(ipoId)` - Get financial data for IPO
- `upsert(ipoId, data)` - Create or update financial data

**DocumentRepository:**
- `findByIPO(ipoId)` - Get all documents for IPO
- `create(ipoId, document)` - Add new document

**ListingPerformanceRepository:**
- `findByIPO(ipoId)` - Get listing performance data
- `upsert(ipoId, data)` - Create or update listing performance

### Cache-Aside Pattern Implementation
**Source:** `docs/architecture.md` lines 149-159, 1070-1073

**Pattern Description:**
1. Check Redis cache before PostgreSQL query
2. On cache miss, query database
3. Populate cache with result and TTL
4. On data updates, explicitly invalidate cache keys
5. If cache fails, proceed with database query (cache failure should not break requests)

**Cache TTL Strategy:**
- IPO list: 15 minutes (900 seconds)
- IPO detail: 30 minutes (1800 seconds)
- Latest subscription: 5 minutes (300 seconds)
- Latest GMP: 10 minutes (600 seconds)
- Historical data: 1 hour (3600 seconds)

*Note: These TTL values are suggested starting points based on cache-aside pattern best practices. Adjust based on actual usage patterns and performance monitoring after implementation.*

**Cache Key Patterns:**
```typescript
// IPO caching
`ipo:slug:{slug}` - Single IPO by slug
`ipo:id:{id}` - Single IPO by ID
`ipo:list:{filterHash}` - IPO list with specific filters

// Subscription caching
`subscription:latest:{ipoId}` - Latest subscription snapshot
`subscription:history:{ipoId}:{days}` - Subscription history

// GMP caching
`gmp:latest:{ipoId}` - Latest GMP record
`gmp:history:{ipoId}:{days}` - GMP history
```

**Cache Invalidation Rules:**
- On IPO create/update: Delete `ipo:slug:{slug}`, `ipo:id:{id}`, all `ipo:list:*`
- On subscription snapshot: Delete `subscription:latest:{ipoId}`
- On GMP record: Delete `gmp:latest:{ipoId}`

**Query Examples Using Drizzle:**

```typescript
import { db } from '@/lib/db';
import { ipos, subscriptions, gmpRecords } from '@/lib/db/schema';
import { eq, and, gte, lte, desc, sql } from 'drizzle-orm';

// Simple query
const ipo = await db.select().from(ipos).where(eq(ipos.slug, slug)).limit(1);

// Query with joins
const ipoWithFinancials = await db.select()
  .from(ipos)
  .leftJoin(financialData, eq(financialData.ipoId, ipos.id))
  .where(eq(ipos.slug, slug));

// Fuzzy search using trigram index
const results = await db.select()
  .from(ipos)
  .where(sql`${ipos.companyName} % ${query}`)
  .orderBy(sql`similarity(${ipos.companyName}, ${query}) DESC`)
  .limit(10);

// Time-series query
const subscriptionHistory = await db.select()
  .from(subscriptions)
  .where(
    and(
      eq(subscriptions.ipoId, ipoId),
      gte(subscriptions.timestamp, startDate)
    )
  )
  .orderBy(desc(subscriptions.timestamp));
```

### Error Handling Strategy
**Source:** `docs/architecture.md` lines 1405-1427, Coding Standards lines 1382-1391

**Critical Rules:**
- All database queries must use try-catch blocks
- If cache fails, log error but proceed with database query
- Repository errors should be specific (e.g., `IPONotFoundError`, `DatabaseError`)
- Log all errors with structured context (query, params, execution time)

**Error Types to Implement:**
```typescript
export class RepositoryError extends Error {}
export class IPONotFoundError extends RepositoryError {}
export class DatabaseConnectionError extends RepositoryError {}
export class CacheError extends RepositoryError {}
```

**Logging Pattern:**
```typescript
try {
  const result = await db.query(...);
  logger.info('IPO query successful', { slug, executionTime });
  return result;
} catch (error) {
  logger.error('IPO query failed', { slug, error });
  throw new DatabaseError('Failed to fetch IPO', { cause: error });
}
```
