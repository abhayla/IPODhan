## Story
**As a** IPODhan platform administrator,
**I want** an automated BSE scraper that extracts IPO data and subscription information from the BSE India website,
**so that** the platform displays comprehensive IPO coverage including BSE-listed and SME IPOs, providing users with complete subscription status across both major exchanges for competitive advantage.

## Acceptance Criteria
1. Scraper successfully navigates to BSE India public issues page (`https://www.bseindia.com/publicissue.html`)
2. Scraper extracts IPO data: company name, issue size, price range, open/close dates, listing exchange (BSE)
3. Scraper extracts subscription data: QIB, NII, Retail, Total subscription figures
4. Scraper validates extracted data using Zod schemas before database insertion
5. Scraper evaluates page structure and selects optimal parsing approach (Cheerio for static HTML or Puppeteer for JavaScript-rendered content)
6. Scraper implements retry logic: 3 retries with exponential backoff (1s, 2s, 4s)
7. Scraper upserts IPO data to PostgreSQL database via IPORepository (merge BSE data with existing NSE data if IPO is listed on both exchanges)
8. Scraper creates subscription snapshots via SubscriptionRepository
9. Scraper invalidates relevant Redis cache keys after successful data update
10. Scraper logs all operations with structured logging (success, failures, duration)
11. Scraper handles errors gracefully and logs failures for monitoring
12. Scraper can be executed manually for testing before scheduling integration (Story 7.4)
13. Scraper correctly identifies and processes SME IPOs with appropriate category tagging

      - Look for IPO data in raw HTML (company names, issue sizes, subscription figures)
      - If IPO table data is visible in source → Likely static HTML (Cheerio candidate)

    - **Step 2 - Network Tab Analysis:** Open DevTools → Network tab → Reload page
      - Check if data is loaded via XHR/Fetch requests (AJAX calls)
      - Look for API endpoints returning JSON with IPO data
      - If data comes from separate API calls → JavaScript-rendered (Puppeteer required)
    - **Step 3 - JavaScript Disable Test:** DevTools → Settings → Debugger → Disable JavaScript → Reload page
      - If IPO table still displays data → Static HTML confirmed (Use Cheerio)
      - If IPO table is empty or broken → JavaScript required (Use Puppeteer)
  - [ ] Apply decision logic based on evaluation results:
    - **Use Cheerio if:** Data is present in view-source AND page works with JavaScript disabled
      - Advantages: 10x faster, no browser overhead, lower memory usage, simpler debugging
      - Trade-off: Cannot handle JavaScript-rendered content
    - **Use Puppeteer if:** Data requires JavaScript OR loaded via AJAX/API calls
      - Advantages: Handles all modern web pages, reuses NSE scraper patterns
      - Trade-off: Slower, higher resource usage, requires browser management
  - [ ] Document decision with evidence:

### Epic 7 Requirements

**Source:** [docs/stories/epics/epic-7-data-pipeline.md]

**BSE Scraper Specifications:**
- URL: `https://www.bseindia.com/publicissue.html`
- Technology: May use Cheerio for static HTML (performance optimization) or Puppeteer if JavaScript-rendered
- Schedule: Every 15 minutes during market hours, 30 minutes after hours (Story 7.4 will implement)
- Data Sources: BSE for BSE-listed and SME IPOs, subscription status, issue details
- Retry Strategy: 3 retries with exponential backoff (1s, 2s, 4s)
- Fallback: IPO Alerts API if scraping fails 3+ times (Story 7.3 will implement)
- Error Handling: Graceful degradation, log failures, continue processing other IPOs
- Monitoring: Structured logs for scraper runs (success/failure metrics)
- SME Focus: BSE is primary exchange for SME IPOs - crucial for comprehensive coverage

**Scraper Pattern (from Epic):**
Same pattern as NSE scraper (Story 7.1) but adapted for BSE:
1. Launch browser or fetch HTML (depending on Cheerio vs Puppeteer decision)
2. Navigate/parse BSE public issues page
3. Extract IPO and subscription data
4. Validate with Zod schemas
5. Upsert to database (with merge logic for dual-listed IPOs)
6. Invalidate cache
7. Log success/failure

**Cache Invalidation Strategy:**
Same as Story 7.1:
1. Delete cache keys:
   - `ipos:list:*` (all listing variations)
   - `ipo:{slug}` (specific IPO if updated)
   - `subscription:latest:{slug}` (if subscription changed)
2. Set "Last Updated" timestamp in database (Story 7.4)

**Data Merge Logic for Dual-Listed IPOs:**
- BSE scraper may find IPOs that are also listed on NSE (already scraped by NSE scraper)
- Must merge exchange information: add 'BSE' to `listingExchanges` array
- Create separate subscription snapshots for each exchange (NSE vs BSE may report different figures)
- Prioritize NSE data for primary fields if discrepancies exist (NSE is more authoritative for mainboard IPOs)

**Data Merge Logic:**
When BSE scraper finds an IPO:
1. Generate slug from company name
2. Query database for existing IPO by slug
3. If exists:

4. If not exists:
   - Create new IPO with `listingExchanges: ['BSE']`
   - Log: "New BSE IPO {slug} created"
5. Create subscription snapshot with `source: 'BSE'` (even if IPO exists with NSE data)

### Repository Pattern Usage

**Source:** [docs/architecture/backend-architecture.md] and Story 2.3

**IPORepository Methods (from Story 2.3):**
- `findBySlug(slug: string): Promise<IPO | null>` - Find IPO by slug
- `findById(id: string): Promise<IPO | null>` - Find IPO by ID
- `create(ipo: IPOInsert): Promise<IPO>` - Create new IPO
- `update(id: string, data: Partial<IPOInsert>): Promise<IPO>` - Update existing IPO
- `findAll(filters: IPOFilters): Promise<PaginatedResponse<IPO>>` - Query with filters

**SubscriptionRepository Methods (from Story 2.3):**
- `createSnapshot(ipoId: string, data: SubscriptionInsert): Promise<Subscription>` - Create subscription snapshot
- `findByIPO(ipoId: string): Promise<Subscription[]>` - Get subscription history
- `findLatest(ipoId: string): Promise<Subscription | null>` - Get latest subscription

**Scraper Usage Pattern for BSE:**
1. **Upsert IPO with Merge Logic:**
   ```typescript
   // Check if IPO exists by slug
   const existingIPO = await IPORepository.findBySlug(slug);
   if (existingIPO) {
     // Merge BSE data
     const updatedExchanges = [...new Set([...existingIPO.listingExchanges, 'BSE'])];
     await IPORepository.update(existingIPO.id, {
       listingExchanges: updatedExchanges,
       // Update other fields if BSE has newer data
     });
   } else {
     // Create new BSE IPO
     await IPORepository.create({
       ...newIPO,
       listingExchanges: ['BSE']
     });
   }
   ```

2. **Create Subscription Snapshot with Source:**
   ```typescript
   // Always create new snapshot (time-series data)
   await SubscriptionRepository.createSnapshot(ipoId, {
     qibSubscription,
     niiSubscription,
     retailSubscription,
     totalSubscription,
     timestamp: new Date(),
     // Note: Add 'source' field if schema supports it (may need to extend schema)
   });
   ```

3. **Cache Invalidation:**
   Same as Story 7.1:
   ```typescript
   await redis.del(`ipo:detail:${slug}`);
   const listKeys = await redis.keys('ipos:list:*');
   await redis.del(...listKeys);
   await redis.del(`subscription:latest:${ipoId}`);
   ```

**Error Handling:**
- Repository methods throw `EntityNotFoundError` if not found
- Repository methods throw `DatabaseError` on database failures
- Scraper should catch these errors, log, and continue processing other IPOs
- Do not crash scraper on single IPO failure

### Cache Invalidation Strategy

**Source:** [docs/architecture/api-specification.md#caching-strategy] and Epic 7

**Cache Keys to Invalidate (from web/lib/cache/cache-keys.ts):**
- `ipo:detail:{slug}` - Specific IPO detail page cache (TTL: 30 minutes)
- `ipos:list:*` - All IPO listing cache variations (TTL: 15 minutes)
  - Pattern includes filters, pagination, sorting variations
  - Use `redis.keys('ipos:list:*')` to find all keys, then `redis.del(...keys)`
- `ipo:search:*` - All IPO search result caches
- `subscription:latest:{ipoId}` - Latest subscription cache (TTL: 5 minutes)
- `subscription:history:{ipoId}:*` - Subscription history cache

**Invalidation Timing:**
- Invalidate AFTER successful database write (upsert or snapshot creation)
- If cache invalidation fails: log error but do not crash scraper
- Cache miss is acceptable (data will be re-fetched from DB)

**Cache-Aside Pattern (from Story 2.3):**
- API routes check Redis first
- On cache miss: query DB, populate cache with TTL
- On data update: explicit cache invalidation (no auto-invalidation)

### Error Handling Strategy

**Source:** [docs/architecture/error-handling-strategy.md] and Epic 7

**BSE Scraper Error Handling:**
1. **Page Fetch/Browser Launch Failures:**
   - Retry 3 times with exponential backoff (1s, 2s, 4s)
   - Log error with context (URL, attempt number)
   - If all retries fail: exit scraper with error code 1, log failure
   - Fallback to IPO Alerts API (Story 7.3 will implement)

2. **Page Load Failures (if using Puppeteer):**
   - Timeout after 30 seconds
   - Retry 3 times
   - Log error with URL and page status
   - If all retries fail: skip scraping for this run, log failure

3. **Data Extraction Failures:**
   - Log error with selector that failed
   - Return empty data array (do not crash scraper)
   - Next scheduled run will retry

4. **Validation Failures:**
   - Log validation error with data sample (redact sensitive info)
   - Skip invalid IPO (do not insert to database)
   - Continue processing other IPOs
   - Track validation failure count in logs

5. **Database Failures:**
   - Retry 3 times with exponential backoff
   - Log error with query context
   - If all retries fail: skip this IPO, log failure
   - Continue processing other IPOs

6. **Cache Invalidation Failures:**
   - Log error
   - Do NOT crash scraper (cache miss is acceptable)
   - Continue processing

**Error Logging Format (Pino):**
```typescript
logger.error({
  error: error.message,
  stack: error.stack,
  context: { url, attempt, duration, scraperSource: 'BSE' },
  timestamp: new Date().toISOString()
}, 'BSE scrape failed');
```

### Performance Considerations

**Source:** Epic 7

**Performance Targets:**
- Scraper execution time: <60 seconds for typical BSE data (10-20 IPOs including SME)
- Database upsert time: <100ms per IPO
- Cache invalidation time: <50ms
- Cheerio parsing time: <2 seconds (if static HTML)
- Puppeteer browser launch time: <3 seconds (if JavaScript-rendered)
- Page load time: <10 seconds (BSE page)

**Optimization Strategies:**
- **Cheerio vs Puppeteer:** Choose Cheerio if BSE uses static HTML (10x faster, no browser overhead)
- **Parallel Processing:** Process multiple IPOs in parallel (use `Promise.all()` for upserts)
- **Connection Pooling:** Reuse database connections (Drizzle ORM handles this)
- **Redis Pipelining:** Batch cache invalidation commands (use `redis.pipeline()`)
- **Efficient Selectors:** Use specific CSS selectors, avoid expensive XPath queries

**Resource Management:**
- Close browser after scraping if using Puppeteer (avoid memory leaks)
- Limit concurrent browser instances (1 for Story 7.2)
- Monitor memory usage (PM2 will track this)
- Cheerio has minimal memory footprint (parse and release)

### Risks and Mitigation

**Source:** Epic 7

**Risk 1: BSE Website Structure Changes**
- **Impact:** Scraper breaks, selectors no longer match, no new data extracted
- **Mitigation:**
  - Use modular selectors (easy to update in one place)
  - Implement snapshot testing (detect structure changes early)
  - Add fallback to IPO Alerts API (Story 7.3)
- **Contingency:**
  - Manual fix within 24 hours (update selectors in `bse-scraper.ts`)
  - Switch to manual seed data updates temporarily

**Risk 2: BSE May Require JavaScript Rendering**
- **Impact:** Cheerio approach fails if BSE page uses JavaScript
- **Mitigation:**
  - Evaluate BSE page structure before implementation
  - Decision task included to choose Cheerio vs Puppeteer
  - If Cheerio fails: switch to Puppeteer (same pattern as NSE)
- **Contingency:**
  - Puppeteer is fallback (already implemented for NSE)

**Risk 3: Data Inconsistencies Between NSE and BSE**
- **Impact:** Dual-listed IPOs show conflicting information
- **Mitigation:**
  - Implement merge logic with NSE data prioritization
  - Create separate subscription snapshots for each exchange
  - Add source attribution on frontend
- **Contingency:**
  - Display exchange-specific data tabs on frontend
  - Allow users to see both NSE and BSE figures

**Risk 4: SME IPO Category Misidentification**
- **Impact:** SME IPOs tagged as MAINBOARD or vice versa
- **Mitigation:**
  - Careful inspection of BSE page structure for category indicators
  - Zod validation for category field
  - Unit tests for SME IPO identification
- **Contingency:**
  - Manual correction of miscategorized IPOs
  - Add admin panel for category overrides (Phase 2)
