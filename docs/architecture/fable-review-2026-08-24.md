## 0. Executive summary (plain English)

The site keeps going wrong in the same *shapes* — a value that was right becomes wrong, a duplicate appears, a repair gets undone — because of five structural properties, not because of any one bug:

1. **The system has no memory.** Every scrape *overwrites* the served row. What was there before is thrown away (`field_sources` keeps one step back; `data_conflicts` only records values when two sources disagree in the same cycle). [corrected per T-314C: Gabion's band collapse is a LIFECYCLE failure, not a first-sight one. Prod `ipos.created_at = 2026-01-02 01:01Z` vs `open_date = 2026-01-05` — the row was born 3 days BEFORE the IPO opened, not six months after it listed; 2026-07-01 is the birth of the *lineage* (`field_sources`) rows, not of the row itself, and this doc's own `traces.md` prints `created_at 2026-01-02` in the same table it drew the "six months after" conclusion from. A settled band was collapsed later (P1-B territory), not born collapsed at first sight (P1-A). This does not undermine the no-memory finding itself — it just means Gabion is not that finding's example.] This is why repairs must come from outside trackers, why "repair before deploy" bites, and why a collapsed band can never widen itself.
2. **Nothing knows what stage an IPO is in when it writes.** Price band, lot size, issue size, and event dates are fixed facts once an IPO opens. The code treats every field as forever re-writable by any source with priority. Every guard built so far (band-narrowing, date sanitizer, subscription floor, offering-type keep, SME/FPO) is a hand-written special case of one missing rule: *settled fields don't change; cumulative fields don't decrease.*
3. **Identity is resolved by name, while the natural keys sit unused.** `resolveIpoRow` (packages/shared/src/repositories/ipo-identity.ts) matches on normalized company name → slug → fuzzy. The scrapers emit `symbol` and `isin`; production has `UNIQUE(symbol)`. Name matching is inherently fuzzy, which is the root of duplicates, the typo bypass, and the 64-row fuzzy corruption.
4. **There is no single write path** — [corrected per T-314C: the "~255 files" headline is struck; it is internally impossible on its face (more files than statements) and ~2.4x too high. T-314C's independent count, matched against the same 25 exported `pgTable` names plus raw INSERT/UPDATE/DELETE: **105 production writer files with ~239 write statements** (web 147, scraper 51, shared 32, +9 raw-only), or 135 files / 525 statements including tests. The **statement** count (~250-260) does reproduce; only the file count was wrong — this doc's own COUNTS table added web's 196 keyword-matched files to other rows' classified file counts, an apples-to-oranges sum.] The web app has ~130 sites including its own scraper module and a generic "write any table by name" admin endpoint, none of which touch the scraper's protected persister — [corrected per T-314C: STRONGER than stated — that endpoint's `validateRecord` fallback returns `{valid:true}` for any table without rules, and only 4 of 25 tables have rules, so it is fail-open for 21 of 25 tables; it also uses ad-hoc `requireAdminAuth()` instead of the project-mandated `withAdminAuth()` wrapper (`.claude/rules/admin-route-auth.md`)]. Even inside the scraper there are two parallel consolidation pipelines plus a legacy fallback that skips sanitising and lineage — [corrected per T-314C: add a third dead-tree finding this doc's P2-F missed: `scraper/src/services/base-scraper-orchestrator.ts` is a 371-line dead duplicate with zero importers].
5. **Existence is mistaken for liveness.** Jobs, flags, gates and checks are written and never scheduled or never reached from what production actually runs (scheduler tree, discovery flag, audit gates, `ENABLE_EARLY_DETECTION` with zero consumers). The 6-round loop found this class in every round.

What this means for the plan: the first review's diagnosis (no single write gateway) is right but incomplete, and its Phase 2 as designed — a chokepoint that *guards mutation* — [corrected per T-314C: this claim ("would still leave properties 1, 2 and 3 in place") is wrong for properties 2 and 3, not just incomplete. **Lifecycle (property 2)** needs only `ipos.status` — a column that already exists on the row being written — and a chokepoint is exactly where that rule belongs: zero new tables. **Identity (property 3)** needs `findByIsin`/`findBySymbol` ahead of the name tiers in the existing `resolveIpoRow` — one function, low-risk given 0 duplicate ISINs and 0 genuine symbol string disagreements (see P1-C below). Only **property 1 (no memory)** genuinely requires the observation log, and its payoff is repairability/auditability, not correctness. So the chokepoint does host cheap fixes for 2 and 3; it does not on its own get you property 1.] A guarded mutation of a row with no memory is still last-write-wins for the one property that actually needs the observation log. The minimal change that removes the recurrence generator is: **make observations first-class and the served row a rebuildable projection with lifecycle rules, keyed by exchange identity** — [corrected per T-314C: sequence the cheap, non-observation-log wins (lifecycle, identity) FIRST, not after the observation log; see §5 for the converged build order] — that is not a rewrite: the consolidation service *is* the resolver already; the observation store is 80% present (`data_conflicts` has values; `field_sources` needs a `value` column and to lose its one-row-per-field uniqueness).

### P1-B — No field lifecycle; every guard is a special case of "settled fields don't change"

[corrected per T-314C — STRUCK: "then 'which scraper emitted min==max' stops mattering" is an over-claim. ## 3. What is GOOD and must not change
- The consolidation service's *shape* (normalise → compare → resolve → record) is the right resolver skeleton; keep it, feed it observations and lifecycle rules.
- Field protection (`field_protection_metadata`, `isIPOLocked`, `filterProtectedFields`) is the right ADMIN-wins model; make it a resolver rule instead of a caller step.
- Deploy pipeline (served-SHA probe, env-parity, migrations-applied, rollback) — mutation-tested, real. Keep.
- The subscription guard's *pattern* (compare against last persisted, not memory) is exactly I3 done right for one table.
- The fleet's checker discipline: 4 of this round's 6 checkers found real gaps the workers missed.
