## Story
**As a** IPODhan platform administrator,
**I want** an automated NSE scraper that extracts IPO data and subscription information from the NSE India website,
**so that** the platform displays fresh, real-time IPO data without manual updates, providing users with accurate subscription status and competitive advantage through up-to-date information.

## Acceptance Criteria
1. Scraper successfully navigates to NSE India public issues page (`https://www.nseindia.com/market-data/public-issues`)
2. Scraper extracts IPO data: company name, issue size, price range, open/close dates, listing exchange
3. Scraper extracts subscription data: QIB, NII, Retail, Total subscription figures
4. Scraper validates extracted data using Zod schemas before database insertion
5. Scraper uses Puppeteer with headless Chrome for JavaScript-rendered content
6. Scraper implements retry logic: 3 retries with exponential backoff (1s, 2s, 4s)
7. Scraper upserts IPO data to PostgreSQL database via IPORepository
8. Scraper creates subscription snapshots via SubscriptionRepository
9. Scraper invalidates relevant Redis cache keys after successful data update
10. Scraper logs all operations with structured logging (success, failures, duration)
11. Scraper handles errors gracefully and logs failures for monitoring
12. Scraper can be executed manually for testing before scheduling integration (Story 7.4)

### Epic 7 Requirements

**Source:** [docs/stories/epics/epic-7-data-pipeline.md]

**NSE Scraper Specifications:**
- URL: `https://www.nseindia.com/market-data/public-issues`
- Technology: Puppeteer 22+ (headless Chrome required for JavaScript-rendered content)
- Schedule: Every 15 minutes during market hours, 30 minutes after hours (Story 7.4 will implement)
- Data Sources: NSE for mainboard IPOs, subscription data, issue details, timelines
- Retry Strategy: 3 retries with exponential backoff (1s, 2s, 4s)
- Fallback: IPO Alerts API if scraping fails 3+ times (Story 7.3 will implement)
- Error Handling: Graceful degradation, log failures, continue processing other IPOs
- Monitoring: Structured logs for scraper runs (success/failure metrics)

**Scraper Pattern (from Epic):**
```javascript
async function scrapeNSE() {
  try {
    // 1. Launch headless browser
    const browser = await puppeteer.launch({ headless: true })

    // 2. Navigate and wait for content
    const page = await browser.newPage()
    await page.goto(NSE_URL)
    await page.waitForSelector('.ipo-table')

    // 3. Extract data
    const ipos = await page.evaluate(() => {
      // DOM parsing logic
    })

    // 4. Validate with Zod
    const validated = IPOSchema.parse(ipos)

    // 5. Upsert to database
    await IPORepository.upsert(validated)

    // 6. Invalidate cache
    await invalidateCache('ipos')

    // 7. Log success
    logger.info({ count: ipos.length }, 'NSE scrape successful')

  } catch (error) {
    logger.error({ error }, 'NSE scrape failed')
    // Fallback to IPO Alerts API (Story 7.3)
  }
}
```

**Cache Invalidation Strategy:**
When new data scraped:
1. Delete cache keys:
   - `ipos:list:*` (all listing variations)
   - `ipo:{slug}` (specific IPO if updated)
   - `subscription:latest:{slug}` (if subscription changed)
2. Set "Last Updated" timestamp in database (Story 7.4)
3. Trigger real-time update via WebSocket (Phase 2 - not in MVP)

- If blocked: increase scraping interval, add stealth plugin, rotate user agents

- `update(id: string, data: Partial<IPOInsert>): Promise<IPO>` - Update existing IPO
- `findAll(filters: IPOFilters): Promise<PaginatedResponse<IPO>>` - Query with filters

**SubscriptionRepository Methods (from Story 2.3):**
- `createSnapshot(ipoId: string, data: SubscriptionInsert): Promise<Subscription>` - Create subscription snapshot
- `findByIPO(ipoId: string): Promise<Subscription[]>` - Get subscription history
- `findLatest(ipoId: string): Promise<Subscription | null>` - Get latest subscription

**Scraper Usage Pattern:**
1. **Upsert IPO:**
   ```typescript
   // Check if IPO exists by slug
   const existingIPO = await IPORepository.findBySlug(slug);
   if (existingIPO) {
     // Update existing IPO
     await IPORepository.update(existingIPO.id, updatedData);
   } else {
     // Create new IPO
     await IPORepository.create(newIPO);
   }
   ```

2. **Create Subscription Snapshot:**
   ```typescript
   // Always create new snapshot (time-series data)
   await SubscriptionRepository.createSnapshot(ipoId, {
     qibSubscription,
     niiSubscription,
     retailSubscription,
     totalSubscription,
     timestamp: new Date()
   });
   ```

3. **Cache Invalidation:**
   ```typescript
   // Invalidate IPO detail cache
   await redis.del(`ipo:detail:${slug}`);
   // Invalidate IPO list cache (all variations)
   const listKeys = await redis.keys('ipos:list:*');
   await redis.del(...listKeys);
   // Invalidate subscription cache
   await redis.del(`subscription:latest:${ipoId}`);
   ```

**Error Handling:**
- Repository methods throw `EntityNotFoundError` if not found
- Repository methods throw `DatabaseError` on database failures
- Scraper should catch these errors, log, and continue processing other IPOs
- Do not crash scraper on single IPO failure

### Cache Invalidation Strategy

**Source:** [docs/architecture/api-specification.md#caching-strategy] and Epic 7

**Cache Keys to Invalidate (from web/lib/cache/cache-keys.ts):**
- `ipo:detail:{slug}` - Specific IPO detail page cache (TTL: 30 minutes)
- `ipos:list:*` - All IPO listing cache variations (TTL: 15 minutes)
  - Pattern includes filters, pagination, sorting variations
  - Use `redis.keys('ipos:list:*')` to find all keys, then `redis.del(...keys)`
- `ipo:search:*` - All IPO search result caches
- `subscription:latest:{ipoId}` - Latest subscription cache (TTL: 5 minutes)
- `subscription:history:{ipoId}:*` - Subscription history cache

**Invalidation Timing:**
- Invalidate AFTER successful database write (upsert or snapshot creation)
- If cache invalidation fails: log error but do not crash scraper
- Cache miss is acceptable (data will be re-fetched from DB)

**Cache-Aside Pattern (from Story 2.3):**
- API routes check Redis first
- On cache miss: query DB, populate cache with TTL
- On data update: explicit cache invalidation (no auto-invalidation)

### Error Handling Strategy

**Source:** [docs/architecture/error-handling-strategy.md] and Epic 7

**Scraper Error Handling:**
1. **Browser Launch Failures:**
   - Retry 3 times with exponential backoff (1s, 2s, 4s)
   - Log error with context (URL, attempt number)
   - If all retries fail: exit scraper with error code 1, log failure
   - Fallback to IPO Alerts API (Story 7.3 will implement)

2. **Page Load Failures:**
   - Timeout after 30 seconds
   - Retry 3 times
   - Log error with URL and page status
   - If all retries fail: skip scraping for this run, log failure

3. **Data Extraction Failures:**
   - Log error with selector that failed
   - Return empty data array (do not crash scraper)
   - Next scheduled run will retry

4. **Validation Failures:**
   - Log validation error with data sample (redact sensitive info)
   - Skip invalid IPO (do not insert to database)
   - Continue processing other IPOs
   - Track validation failure count in logs

5. **Database Failures:**
   - Retry 3 times with exponential backoff
   - Log error with query context
   - If all retries fail: skip this IPO, log failure
   - Continue processing other IPOs

6. **Cache Invalidation Failures:**
   - Log error
   - Do NOT crash scraper (cache miss is acceptable)
   - Continue processing

**Error Logging Format (Pino):**
```typescript
logger.error({
  error: error.message,
  stack: error.stack,
  context: { url, attempt, duration },
  timestamp: new Date().toISOString()
}, 'NSE scrape failed');
```

- **Zod Validation (Primary Defense):**
  - All scraped data validated with Zod schemas before database insertion
  - Schemas enforce type safety, format validation, business rules
  - Invalid data rejected and logged (never inserted to DB)

- **Additional Sanitization Layers:**
  - **HTML/Script Injection Prevention:**
    - Escape HTML entities in extracted text fields (company names, descriptions)
    - Use DOMPurify or similar library if storing any HTML content
    - Strip `<script>`, `<iframe>`, and other dangerous tags

  - **SQL Injection Prevention:**
    - Use Drizzle ORM parameterized queries exclusively (never raw SQL with string concatenation)
    - Repository layer already provides SQL injection protection
    - Never construct queries with unsanitized user input or scraped data

  - **NoSQL Injection Prevention:**
    - Validate Redis keys before use (no user input in cache keys)
    - Use predefined cache key templates from `web/lib/cache/cache-keys.ts`
    - Never use scraped data directly as Redis keys without validation

  - **Path Traversal Prevention:**
    - Do not use scraped data to construct file paths
    - If file operations needed: whitelist allowed paths, validate against allowed patterns

  - **Command Injection Prevention:**
    - Never execute shell commands with scraped data
    - Avoid `eval()`, `Function()`, or other dynamic code execution with external data

- **Data Sanitization Examples:**
  ```typescript
  // Company name sanitization
  function sanitizeCompanyName(name: string): string {
    return name
      .trim()
      .replace(/[<>]/g, '') // Remove angle brackets
      .slice(0, 200); // Limit length
  }

  // Numeric sanitization
  function sanitizeSubscriptionNumber(value: any): number {
    const parsed = parseFloat(value);
    if (isNaN(parsed) || parsed < 0) {
      throw new Error('Invalid subscription number');
    }
    return Math.min(parsed, 10000); // Cap at reasonable max (10000x subscribed)
  }
  ```

### TypeScript Path Aliases Configuration

**Source:** [docs/architecture/unified-project-structure.md]

**Problem:** Scraper workspace needs to import from web workspace (repositories, database client, Redis client). Without path aliases, imports become brittle with relative paths like `../../web/lib/repositories/ipo-repository`.

```json
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler", // or "node16" for Node.js ESM

    "paths": {
      "@web/*": ["../web/*"],
      "@shared/*": ["../packages/shared/src/*"],
      "@scraper/*": ["./src/*"]
    },
    "esModuleInterop": true,
    "resolveJsonModule": true,
    "strict": true,
    "skipLibCheck": true,
    "forceConsistentCasingInFileNames": true
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist"]
}
```

**Usage Examples:**

### Risks and Mitigation

**Source:** Epic 7

**Risk 1: NSE Website Structure Changes**
- **Impact:** Scraper breaks, selectors no longer match, no new data extracted
- **Mitigation:**
  - Use modular selectors (easy to update in one place)
  - Implement snapshot testing (detect structure changes early)
  - Add fallback to IPO Alerts API (Story 7.3)
- **Contingency:**
  - Manual fix within 24 hours (update selectors in `nse-scraper.ts`)
  - Switch to manual seed data updates temporarily
  - Story 7.3 provides API fallback

**Risk 2: Anti-Bot Detection Blocks Scraper**
- **Impact:** NSE blocks Puppeteer requests, scraping fails consistently
- **Mitigation:**
  - Use proper user agent (standard Chrome)
  - Add Puppeteer stealth plugin (puppeteer-extra-plugin-stealth) if blocked
  - Rotate user agents if needed
  - Polite scraping (reasonable intervals, not hammering server)
- **Contingency:**
  - Increase scraping interval (reduce request frequency)
  - Use IPO Alerts API as primary source (Story 7.3)
  - Consider paid proxy service if severe blocking

**Risk 3: Database Connection Failures**
- **Impact:** Scraped data cannot be persisted, cache invalidation fails
- **Mitigation:**
  - Implement retry logic (3 attempts, exponential backoff)
  - Use connection pooling (Drizzle ORM handles this)
  - Log all database errors for monitoring
- **Contingency:**
  - Next scheduled scraper run will retry
  - Alert admin if 3+ consecutive failures (Story 7.5)
  - Manual database check and restart if needed

**Risk 4: Incomplete or Inaccurate Subscription Data**
- **Impact:** Subscription figures shown on site are outdated or incorrect
- **Mitigation:**
  - Scrape NSE as primary source (most authoritative)
  - Cross-reference with BSE data (Story 7.2)
  - Add data source attribution on frontend
- **Contingency:**
  - Display "Last updated: X minutes ago" on frontend
  - Allow users to report data issues
