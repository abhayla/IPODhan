    'use client';

    import { Component, ReactNode } from 'react';

    interface Props {
      children: ReactNode;
    }

    interface State {
      hasError: boolean;
    }

    export class IPOTablesErrorBoundary extends Component<Props, State> {
      constructor(props: Props) {
        super(props);
        this.state = { hasError: false };
      }

      static getDerivedStateFromError() {
        return { hasError: true };
      }

      render() {
        if (this.state.hasError) {
          return (
            <div className="container mx-auto px-4 py-12 text-center">
              <p className="text-muted-foreground">

              </p>
            </div>
          );
        }

        return this.props.children;
      }
    }

### Server-Side Data Fetching Context

**Next.js Server Components** [Source: docs/architecture/frontend-architecture.md]:
- App Router pages are React Server Components by default
- Can use async/await for data fetching
- Data fetched on server, HTML sent to client
- No client-side hydration needed for static data

**ISR (Incremental Static Regeneration)**:
- Static page generated at build time
- Revalidated every N seconds (background regeneration)
- Serves stale-while-revalidate pattern
- Export constant: `export const revalidate = 300;` (5 minutes)

**Example Pattern**:
```typescript
// Export revalidate for ISR
export const revalidate = 300; // 5 minutes

// Async server component
export default async function Home() {
  // Server-side data fetching
  const data = await fetchData();

  // Render with fetched data
  return <div>{data}</div>;
}
```

### Performance Considerations

**Performance Targets** [Source: docs/architecture/security-and-performance.md]:
- **LCP (Largest Contentful Paint)**: <2.5s (target: <2s)
- **FID (First Input Delay)**: <100ms
- **CLS (Cumulative Layout Shift)**: <0.1
- **Lighthouse Performance Score**: >90

**Optimization Strategies**:
1. **ISR with 5-minute revalidation**: Page statically generated, fast serve
2. **Server-side data fetching**: Data ready before HTML sent to client
3. **Redis caching**: Service layer uses Redis (sub-millisecond latency)
4. **Parallel fetching**: Promise.all fetches all 4 datasets simultaneously
5. **Limited data**: Max 10 items per table (40 total rows) - very lightweight
6. **Skeleton loading**: Prevents CLS during SSR
7. **No client-side JavaScript for data**: Pure server components, less bundle size

**Bundle Size Impact**:
- HomeIPOTablesSection is server component (no client JS)
- Only client component is error boundary (minimal JS)
- Expected bundle size increase: <5KB

**Database Impact**:
- 4 database queries (via repository layer)
- Each query limited to 10 results
- Redis cache hit: <10ms per query
- Redis cache miss: <100ms per query (with indexes)
- Total data fetch time: <50ms (cache hit) or <400ms (cache miss)

  - Aligns with Next.js App Router best practices
  - No interactivity needed in home page itself

**Decision 2: ISR with 5-Minute Revalidation**
- **Decision**: Use ISR with `revalidate = 300` (5 minutes)
- **Rationale**:
  - Static page for fast serving
  - Background revalidation keeps data fresh
  - Balance between freshness and server load
  - IPO data doesn't change every second
  - Redis cache in service layer provides additional freshness
  - Aligns with performance targets (LCP <2s)

**Decision 3: Error Handling with Empty Arrays**
- **Decision**: Return empty arrays on error, show empty states
- **Rationale**:
  - Graceful degradation (page always renders)
  - Better UX than error page
  - Other sections (Hero, Features, CTA) still functional
  - User can refresh to retry
  - Errors logged for debugging

**Decision 4: Structured Data for SEO**
- **Decision**: Add IPO listings structured data (ItemList schema)
- **Rationale**:
  - Improves search engine understanding of page content
  - Potential for rich snippets in search results
  - Aligns with financial product schema standards
  - Low implementation cost, high SEO benefit
  - Helps with "IPO 2025" keyword rankings

**Decision 5: No Loading State for Server Component**
- **Decision**: No loading spinner/state for initial page load
- **Rationale**:
  - Server component renders with data on first paint
  - Skeletons only needed if using Suspense (not needed here)
  - ISR means page is pre-rendered (instant serve)
  - Loading state only relevant for client-side fetching
