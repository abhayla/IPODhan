### Error Handling Strategy
**Source:** [docs/architecture/error-handling-strategy.md]

**Error Response Format (from backend):**
```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "IPO not found",
    "details": {},
    "timestamp": "2025-01-05T10:30:00.000Z",
    "requestId": "req_abc123"
  }
}
```

**Frontend APIError Class (to implement):**
```typescript
class APIError extends Error {
  code: string;           // Error code from backend
  status: number;         // HTTP status code
  details?: object;       // Additional error context
  requestId?: string;     // Request ID for debugging

  // User-friendly message translation
  getUserMessage(): string {
    // Map error codes to friendly messages
  }
}
```

**Error Flow:**
1. API client catches fetch errors
2. Parses backend error response
3. Creates APIError instance
4. Logs to console (dev) or Sentry (prod)
5. Returns error to component
6. Component displays user-friendly message

**Retry Logic:**
- Retry on network errors (ECONNREFUSED, timeout)
- Exponential backoff: 1s, 2s, 4s
- Max 3 retries
- Do NOT retry on 4xx errors (client errors)

### Request/Response Flow

**Typical API Call Flow:**
1. Component calls `apiClient.getIPOs({ status: 'OPEN' })`
2. API client constructs URL: `/api/ipos?status=OPEN`
3. API client adds headers (Content-Type, etc.)
4. Request interceptor logs request
5. Fetch sends request to backend
6. Backend returns JSON response
7. Response interceptor logs response
8. API client parses response
9. If error: Create APIError, retry if network error
10. If success: Validate response with Zod, return typed data
11. Component receives typed data or APIError
