## Story
**As a** IPO investor visiting IPODhan,
**I want** pages to load in under 2 seconds with smooth, responsive interactions,
**so that** I can quickly access IPO information without frustration, especially during critical IPO subscription periods when time is of the essence.

## Acceptance Criteria
1. Lighthouse Performance score: >90 on all major pages (homepage, IPO listing, IPO detail)
2. Largest Contentful Paint (LCP) <2.5s on 3G connection for all pages
3. First Input Delay (FID) <100ms for all interactive elements
4. Cumulative Layout Shift (CLS) <0.1 on all pages (no visual jumping during load)
5. API response time (p95): <500ms for all endpoints measured under realistic load
6. Initial JavaScript bundle <200KB gzipped for main page routes
7. Database queries optimized: No N+1 query problems, all queries <100ms with proper indexes verified
8. Redis caching implemented for all data endpoints with appropriate TTLs (5min list, 15min detail, 10min subscription)
9. All images optimized: WebP format with fallback, lazy loading below fold, responsive srcset
10. Fonts optimized: next/font subsetting and preloading for critical fonts
11. Performance monitoring baseline established: Document current metrics for ongoing tracking
12. Performance test suite created: Automated tests verify performance targets in CI/CD

### Caching Strategy
[Source: architecture/security-and-performance.md#caching-strategy]

**Redis Cache TTLs:**
| Data Type | Cache TTL | Invalidation Trigger |
|-----------|-----------|---------------------|
| IPO List | 5 min | On scraper update |
| IPO Detail | 15 min | On scraper update |
| Subscription | 10 min | On scraper update |
| GMP History | 30 min | On manual entry |

**Cache-Aside Pattern:**
1. Check Redis before PostgreSQL
2. Populate cache on miss with appropriate TTL
3. Explicit invalidation on data updates

**Cache Key Naming Convention:**
- `ipo:list:{filterHash}` - IPO listings with filters
- `ipo:detail:{slug}` - IPO detail page
- `ipo:subscription:{slug}` - Subscription data

**Stale-While-Revalidate:**
- Serve stale content while revalidating in background
- Reduces perceived latency for users
- Configure in Next.js API route headers
