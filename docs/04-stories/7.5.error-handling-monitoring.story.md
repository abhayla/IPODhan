## Story
**As a** IPODhan platform administrator,
**I want** comprehensive error handling, monitoring, and alerting for the data pipeline with detailed scraper logs and metrics tracking,
**so that** I can maintain 95%+ scraper uptime, quickly identify and resolve issues, and ensure users always see reliable IPO data with graceful degradation when scrapes fail.

## Acceptance Criteria
1. `scraper_logs` database table created with proper schema (id, source, status, records_processed, records_failed, duration_ms, error_message, error_stack, created_at) and index on created_at
2. All scrapers (NSE, BSE, API Fallback) write success/failure logs to database after each execution
3. Success/failure metrics tracked in Redis with rolling 24-hour window: `scraper:{source}:success_count`, `scraper:{source}:failure_count` with 24h TTL
4. Alert triggers after 3+ consecutive failures: log ERROR level message, set Redis flag `scraper:{source}:alert_sent` with 1h TTL
5. Alert triggers if success rate < 80% in last 24 hours: log WARN level with recent error summary
6. Monitoring dashboard API endpoint `GET /api/admin/scraper/status` returns scraper status for NSE, BSE, API fallback with lastRun, lastSuccess, lastFailure, successRate24h, consecutiveFailures, recordsProcessed24h
7. Health status calculated correctly: HEALTHY (>90% success rate), DEGRADED (70-90%), CRITICAL (<70% or down >2 hours)
8. Graceful degradation implemented: when all scrapers fail, show last known data with "Last updated: X hours ago" message
9. Frontend displays "Last updated" timestamp and outdated data banner when data is stale (>2 hours old)
10. Email alerting service implemented (optional) using Nodemailer or equivalent
11. Log retention policy: Automated cleanup job removes logs older than 30 days
12. Integration test: Verify monitoring and alerting work end-to-end (trigger failure, verify alert)

### Epic 7 Requirements

**Source:** [docs/epics/epic-7-sharded.md#story-75-error-handling--monitoring]

**Error Logging Requirements:**
- Store scraper logs in `scraper_logs` table
- Schema: id, source, status, records_processed, records_failed, duration_ms, error_message, error_stack, created_at
- Index on created_at for efficient querying
- Retention policy: Keep logs for 30 days

**Success/Failure Metrics:**
- Track in Redis with rolling 24h window
- Keys: `scraper:{source}:success_count`, `scraper:{source}:failure_count`
- TTL: 24 hours
- Calculate success rate: `success / (success + failure) * 100`
- Expose metrics endpoint: `GET /api/admin/scraper/metrics`

**Alerting Logic:**
- Alert if 3+ consecutive failures:
  - Log error with level "ERROR"
  - Send email to admin (optional)
  - Set Redis flag: `scraper:{source}:alert_sent` (TTL: 1h)
- Alert if success rate < 80% in last 24 hours:
  - Log warning with level "WARN"
  - Include recent error summary in alert

**Monitoring Dashboard API:**
- Endpoint: `GET /api/admin/scraper/status`
- Response includes per-scraper status: lastRun, lastSuccess, lastFailure, successRate24h, consecutiveFailures, recordsProcessed24h
- Health status logic:
  - HEALTHY: All scrapers > 90% success rate
  - DEGRADED: Any scraper 70-90% success rate
  - CRITICAL: Any scraper < 70% success rate or down > 2 hours

**Graceful Degradation:**
- When all scrapers fail:
  - Show last known data with "Last updated: X hours ago" message
  - Display banner: "IPO data may be outdated. We're working on it."
  - Log critical error for immediate investigation

```sql
CREATE TABLE scraper_logs (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  source TEXT NOT NULL,                    -- 'NSE' | 'BSE' | 'API_FALLBACK'
  status TEXT NOT NULL,                     -- 'SUCCESS' | 'FAILURE' | 'PARTIAL'

  records_failed INTEGER DEFAULT 0,

  error_stack TEXT,
  created_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_scraper_logs_created_at ON scraper_logs(created_at DESC);
CREATE INDEX idx_scraper_logs_source_created_at ON scraper_logs(source, created_at DESC);
CREATE INDEX idx_scraper_logs_status ON scraper_logs(status);
```

**Index Strategy:**
- Primary index on `created_at DESC` for recent log queries
- Composite index on `(source, created_at)` for source-specific queries
- Index on `status` for filtering by success/failure

### Risks and Mitigation

**Source:** Epic 7

**Risk 1: Database grows too large with logs**
- **Impact:** Performance degradation, storage costs
- **Mitigation:**
  - Automated log retention (30 days)
  - Daily cleanup job removes old logs
  - Indexes optimize query performance
- **Contingency:**
  - Reduce retention to 14 days if needed
  - Archive old logs to S3 (Phase 2)

**Risk 2: Email alerts fail to send**
- **Impact:** Admin not notified of critical issues
- **Mitigation:**
  - Console logging always works (fallback)
  - Email is optional enhancement
  - Alert cooldown prevents spam
- **Contingency:**
  - Monitor console logs via PM2
  - Use external monitoring service (Sentry)

**Risk 3: Redis metrics lost on restart**
- **Impact:** Temporary loss of 24h success rate data
- **Mitigation:**
  - Metrics rebuild from database logs on restart
  - 24h rolling window recovers quickly
- **Contingency:**
  - Query database for recent logs to recalculate metrics
