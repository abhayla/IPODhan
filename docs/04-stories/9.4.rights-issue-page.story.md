## Story

**As a** retail investor interested in Rights Issues,
**I want** a dedicated Rights Issue page with tabbed navigation and comprehensive issue details,
**so that** I can track upcoming and live Rights Issues and make informed investment decisions based on Record Date, Open Date, and Renunciation Date.

## Acceptance Criteria

1. Rights Issue page accessible at `/rights-issues`
2. Two tabs: "Upcoming" and "Live" with proper filtering
3. Table displays: Issuer Company, Record Date, Open Date, Renunciation Date
4. Tab state persists in URL query params
5. "More Rights Issues..." link from home page navigates correctly
6. Page uses ISR with 5-minute revalidation
7. Responsive: table on desktop, cards on mobile
8. Empty state shows "No rights issues available" message
9. Loading skeleton displays during data fetch
10. SEO metadata configured (title, description, structured data)
11. Page renders successfully even if API call fails (graceful degradation)

### Caching Strategy Context

**Cache-Aside Pattern** [Source: CLAUDE.md]:
1. Check Redis for cached data using cache key
2. If cache hit: Parse JSON and return
3. If cache miss: Fetch from API
4. Store result in Redis with TTL
5. Return data to caller

**Cache Keys**:
- Upcoming: `rights:upcoming`
- Live: `rights:live`

**Cache TTL**: 300 seconds (5 minutes)

**Redis Error Handling**:
- Cache errors logged but don't break functionality
- Application continues functioning if Redis unavailable
- Falls back to API calls without caching

### Key Decisions & Rationale

**Decision 1: Temporary Field Mapping**
- **Decision**: Use temporary mapping (recordDate → openDate, renunciationDate → closeDate)
- **Rationale**:
  - Schema doesn't have dedicated fields yet
  - Allows implementation to proceed without schema changes
  - Easy to update when schema is enhanced
  - Isolated to single function (transformRightsData)

**Decision 2: DataTable Component Reuse**
- **Decision**: Use existing DataTable component instead of creating new table
- **Rationale**:
  - DRY principle (Don't Repeat Yourself)
  - Tested, production-ready component
  - Consistent UX across all pages
  - Reduced development time and maintenance

**Decision 3: Client-Side Tabs with URL State**
- **Decision**: Client-side tabs with URL query params (`?tab=upcoming`)
- **Rationale**:
  - Shareable URLs (users can share specific tab)
  - Browser history support (back/forward buttons work)
  - Better UX (instant tab switching)
  - SEO-friendly (search engines can index both states)

**Decision 4: Parallel Data Fetching**
- **Decision**: Fetch both tabs' data in parallel with `Promise.all()`
- **Rationale**:
  - Faster initial page load
  - Data ready for both tabs immediately
  - Tab switching is instant (no loading state)
  - Minimal performance impact (Rights Issues data is small)
