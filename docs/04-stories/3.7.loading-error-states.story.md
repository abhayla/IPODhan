## Story
**As a** user interacting with the IPO dashboard and its features,
**I want** to see clear loading indicators, helpful error messages, and appropriate empty states,
**so that** I understand what the application is doing, can recover from errors gracefully, and have a smooth user experience even when things go wrong.

## Acceptance Criteria
1. Loading skeletons for IPO cards during initial page load and pagination
2. Loading spinner for page transitions and navigation
3. Error boundary component catches unhandled React errors
4. Network error handling with user-friendly messages
5. Empty state component for when no IPOs match filters/search
6. Retry mechanisms for failed API requests
7. Toast notifications for errors and success messages
8. Graceful degradation when features are unavailable

## States to Handle
1. **Initial Loading** - First page load, fetch IPO data
2. **Pagination Loading** - Loading next/previous page of results
3. **Filter/Search Loading** - Applying filters or searching
4. **Network Errors** - API failures, timeout, offline
5. **Empty Results** - No IPOs match current filters/search
6. **Rate Limiting Errors** - Too many requests (future-proofing)

### API Client Error Handling
**Source:** [docs/architecture/error-handling-strategy.md]

**API Error Format (from backend):**
```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "IPO not found",
    "details": {},
    "timestamp": "2025-01-05T10:30:00.000Z",
    "requestId": "req_abc123"
  }
}
```

**APIError Class (frontend):**
```typescript
// web/lib/errors/APIError.ts
export class APIError extends Error {
  constructor(
    public statusCode: number,
    public code: string,
    message: string,
    public details?: Record<string, any>
  ) {
    super(message);
    this.name = 'APIError';
  }

  static fromResponse(response: Response, body: any): APIError {
    return new APIError(
      response.status,
      body?.error?.code || 'UNKNOWN_ERROR',
      body?.error?.message || 'An error occurred',
      body?.error?.details
    );
  }

  getUserMessage(): string {
    // Map technical errors to user-friendly messages
    const messages: Record<number, string> = {
      404: 'The requested resource was not found.',
      500: 'Server error. Please try again later.',
      503: 'Service temporarily unavailable.',
    };
    return messages[this.statusCode] || this.message;
  }
}
```

**Retry Logic (api-client.ts):**
```typescript
async function fetchWithRetry(
  url: string,
  options: RequestInit,
  maxRetries = 3
): Promise<Response> {
  let lastError: Error;
  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      const response = await fetch(url, options);
      if (response.ok || response.status < 500) {
        return response; // Success or client error (don't retry)
      }
      throw new Error(`HTTP ${response.status}`);
    } catch (error) {
      lastError = error as Error;
      if (attempt < maxRetries) {
        await delay(Math.pow(2, attempt) * 1000); // Exponential backoff
      }
    }
  }
  throw lastError!;
}
```

### Error Handling Strategy
**Source:** [docs/architecture/error-handling-strategy.md]

**Error Levels:**
1. **Component-level errors:** Try/catch in event handlers, show inline error
2. **Route-level errors:** error.tsx catches rendering errors, shows full-page error
3. **Global errors:** ErrorBoundary catches unhandled errors, shows fallback UI
4. **Network errors:** API client catches, maps to APIError, shows toast

**Error Logging:**
- **Development:** console.error with full stack trace
- **Production:** Sentry.captureException with context (user, request, component)

**User Messaging:**
- NEVER expose technical details (stack traces, SQL errors)
- ALWAYS provide actionable guidance ("Try again", "Check connection")
- SHOW retry options when applicable
- INCLUDE support contact for persistent errors
