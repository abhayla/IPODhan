# Story 7.6b: Alternative Data Sources - Infrastructure Components

## Status

## Story
**As a** IPODhan platform administrator,
**I want** the alternative data source scrapers to be fully integrated with the production infrastructure,
**so that** Moneycontrol and Chittorgarh scrapers run automatically on schedule, persist data including GMP to the database, and integrate with the monitoring dashboard.

## Context
This story contains the infrastructure components that were intentionally separated from Story 7.6a (core implementation) to be deployed directly on the VPS server. Story 7.6a implemented all the core scraping logic, validation, and tests. This story (7.6b) handles the production infrastructure integration.

8. Monitoring dashboard shows Moneycontrol scraper metrics
9. Monitoring dashboard shows Chittorgarh scraper metrics
10. Alert thresholds configured (3+ failures, <80% success rate)
11. Health check endpoint reports Moneycontrol scraper status
12. Health check endpoint reports Chittorgarh scraper status

14. Scraper failure rate monitored and alerted if >20% over 1 hour

## Implementation Notes

### Why VPS-Only Implementation?
1. **Database Access**: Migration requires direct production database access
2. **Scheduler State**: Scheduler jobs need to maintain state on production
3. **Monitoring Integration**: Metrics need to flow to production monitoring
4. **Environment Variables**: Production secrets and configs only on VPS
5. **Resource Management**: Production server has different resource constraints

### Deployment Steps
1. SSH to VPS server
2. Pull latest code from main branch (Story 7.6a)
3. Run database migration
4. Update scheduler configuration
5. Restart scheduler service
6. Verify scrapers run on schedule
7. Monitor metrics dashboard

## Risks & Mitigation

### Risk 1: Database Migration Failure
- **Mitigation**: Test migration on staging first, have rollback script ready

### Risk 2: Scheduler Overload
- **Mitigation**: Staggered execution, monitor resource usage

### Risk 3: API Rate Limiting
- **Mitigation**: Conservative schedules, exponential backoff already implemented

## Rollback Plan

### Database Migration Rollback
If the migration causes issues, execute the following rollback script:

```sql
-- Rollback script (save as rollback-7.6b-migration.sql)
-- Backup data before rollback
CREATE TABLE ipos_backup_7_6b AS SELECT * FROM ipos;

-- Remove added columns
ALTER TABLE ipos DROP COLUMN IF EXISTS gmp;
ALTER TABLE ipos DROP COLUMN IF EXISTS gmp_percentage;
ALTER TABLE ipos DROP COLUMN IF EXISTS gmp_updated_at;
ALTER TABLE ipos DROP COLUMN IF EXISTS rating;
ALTER TABLE ipos DROP COLUMN IF EXISTS listing_gains;
ALTER TABLE ipos DROP COLUMN IF EXISTS data_sources;

-- Verify rollback
SELECT column_name FROM information_schema.columns
WHERE table_name = 'ipos'
ORDER BY ordinal_position;
```

**Rollback Steps:**
1. Stop scheduler service: `pm2 stop ipodhan-scraper`
2. Execute rollback script: `psql -U postgres -d ipodhan -f rollback-7.6b-migration.sql`
3. Verify columns removed
4. Git revert to previous stable commit
5. Restart services: `pm2 restart all`
6. Monitor for 1 hour to ensure stability

**Data Validation Post-Rollback:**
- Verify IPO count unchanged: `SELECT COUNT(*) FROM ipos;`
- Verify no data loss in core fields
- Check application functionality
- Review error logs

### Scheduler Rollback
If scheduler integration causes conflicts:

```bash
# Revert scheduler.ts to previous version
git checkout HEAD~1 -- scraper/src/scheduler/scheduler.ts

# Rebuild and restart
cd scraper && npm run build
pm2 restart ipodhan-scraper

# Verify only NSE and BSE jobs running
pm2 logs ipodhan-scraper --lines 50
```
