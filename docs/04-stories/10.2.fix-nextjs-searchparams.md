**Note on sme-ipos and mainboard-ipos pages**: These pages use `searchParams?: { [key: string]: ... }` (optional) with optional chaining (`searchParams?.year`). While this works without errors, the idiomatic Next.js 15 pattern is `searchParams: Promise<{ ... }>` with await. This is a minor code quality issue, not a functional bug.

### Client Component Usage (Correct Pattern - No Changes Needed)
Client components use `useSearchParams()` hook from `next/navigation`:
```typescript
'use client';
import { useSearchParams } from 'next/navigation';
const searchParams = useSearchParams(); // Hook, not awaited
const year = searchParams.get('year'); // Synchronous access is correct
```

### API Routes (Correct Pattern - No Changes Needed)

```typescript
export async function GET(request: NextRequest) {
  const searchParams = request.nextUrl.searchParams; // Synchronous access is correct
  const page = searchParams.get('page');
}
```

### Technical Details

**Next.js 15 Breaking Change**:
- In Next.js 15, `searchParams` prop is now a Promise
- Must be awaited before accessing any properties
- Applies to all Server Components receiving searchParams
- Affects: `page.tsx`, `layout.tsx`, `route.ts` files

**TypeScript Type Definition**:
```typescript
type Props = {
  searchParams: Promise<{ [key: string]: string | string[] | undefined }>
}
```

**Common Affected Patterns**:
```typescript
// ❌ All these patterns are BROKEN in Next.js 15:
searchParams.year
searchParams.page
searchParams.category
Object.keys(searchParams)
Object.entries(searchParams)

// ✅ Correct pattern:
const params = await searchParams;
params.year
params.page
params.category
Object.keys(params)
Object.entries(params)
```
