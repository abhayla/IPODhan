## Pre-made design decisions (the run must NOT pause on these)

**The eighteen decisions already in §0.0.1 (OD-1 … OD-18) stand unchanged.** The following were decided by the owner on 2026-09-09 in the intake interview for this contract and MUST be added to §0.0.1 as OD-19 … OD-26, quoted as below, dated 2026-09-09, each pointing at the section that implements it, each with a D10 signature. The corresponding rows in §0.0.2 (O-1, O-2, O-3) move to §0.0.1; O-7 stays in §0.0.2 as a standing constraint.

1. **OD-19, O-1 cadence — four jobs, no timer on documents.** Owner: *"Offer document never on a clock. Live figures only during bidding. Subscription-related work can run every hour or even thirty minutes, but not the scraper that is fetching the IPO data. Three runs a day, midnight, eight in the morning, two in the afternoon. Add another cycle at ten o'clock at night that deals only with old IPOs, latest closed first, at most 10 old IPOs a day, do not repeat which are already done."*
   - **Data job** at 00:00, 08:00, 14:00 IST: discovery, document download and extraction, per-field pull, verification reads. Verification reads go **exchanges first (NSE, then BSE), then websites** (owner). Never re-reads a document on a timer: a document is read once on arrival, again only when a newer document type arrives or the re-read loop (§3) asks.
   - **Live-figures job** every 30 minutes, 10:00–18:30 IST, only on days when at least one IPO is OPEN: subscription, demand graph, GMP. Touches nothing else. (Owner allowed 30 or 60 minutes; 30 chosen because the job is a few web calls and the exchanges publish the final day's figure after 17:00.)
   - **Closed-IPO job** at 22:00 IST: only IPOs with `status` LISTED or CLOSED whose close date is before today, ordered by close date descending, at most 10 IPOs per night, each IPO marked done in a persistent marker (a column or table the design specifies) so it is never picked twice; a failed IPO is marked with its cause and retried only when the cause class changes.
   - **No job ever kills a running cycle.** The PM2 `cron_restart` force-kill goes; each job is started by a scheduler that skips the start when the cycle lock is held. With the kill gone, the design raises the extraction cap from 10 to 30 minutes and the wake budget from 20 to 50 minutes and states the new lock TTL derivation.
   - The design's §2.1 / D-13 and §5.1 are rewritten to this. Any earlier text saying "every 30 minutes" for anything other than the live-figures job is a defect. Consistency check **D12** enforces: the document names exactly these four jobs with these times, and no section schedules a document read on an interval.
2. **OD-20, O-2 money — crore is the default for every amount column.** Owner: *"Crore should be the default for every amount column."* Every column holding a rupee amount stores crore as `numeric(12,2)` (999.99 means Rs 999.99 crore); the design lists every such column by table and name with its current unit, the exact conversion, and the source-backed repair for existing rows (a re-runnable tool that proves each converted value against the source document or exchange payload, never arithmetic on the stored number). Per-share prices, percentages, share counts and subscription multiples are not amounts and are unchanged. The public API serves both the new crore field and the old field for one release, then the old field is retired; the design names each API route and web formatter affected. Build item 11 is un-blocked and must be fully carded. Check **D13**: the amount-column inventory in the design equals the set of `numeric`/`bigint` money columns in `schema.ts` that the probe `probes/amount-columns.mjs` classifies as amounts, with zero unclassified.
3. **OD-21, O-3 — per-field validation before write, no timed retry.** Owner: *"Go with your recommendation"* (option A). Every extracted field is validated on its own before the write; a failing field is dropped, recorded in a failure row carrying field, IPO, document, rule id and cause text; the remaining fields are written; the pull loop asks rank 2 for the dropped field. ## Failure-recovery budget

- **Per-stage fix budget:** 10 attempts on a red gate, then log DEFECTED with the exact failing check and move to the next stage that does not depend on it; never halt the run for one check.
- **Probe failures:** a source that returns an error or a block page gets 3 attempts spaced 2 minutes apart with a browser-like user agent; then the row's evidence says `unreachable on <date>, rank carried as judgement` and the final report lists it. Never fabricate a payload.
- **Reviewer non-return or over-budget:** one re-dispatch with a halved brief; then proceed with the two reviews that returned and record the gap as a provisional item.
- **Tunnel down:** restart per `docs/ops/prod-ops-recipes.md` §1, twice; then use staging for reads that allow it and record which numbers are staging rather than production.
- **Hard halt only for:** a contradiction between two owner decisions in §0.0.1 (record it as O-nn and stop, since both are the owner's words); the worktree assertion failing; a credential missing from `D:\Abhay\GLOBAL.env`; a write outside scope detected. Context-budget anxiety is not a halt: append a continuation note to the progress log and keep going in the next context.
